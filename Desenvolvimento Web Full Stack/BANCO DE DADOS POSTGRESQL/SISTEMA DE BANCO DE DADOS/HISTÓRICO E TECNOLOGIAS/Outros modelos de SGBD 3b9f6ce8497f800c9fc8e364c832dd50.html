Outros modelos de SGBD

Outros Modelos de SGBD

Embora os SGBDs relacionais sejam extremamente importantes e ainda sejam muito utilizados, eles não são a única forma de organizar e gerenciar dados.

Dependendo da aplicação, pode ser mais adequado utilizar outros modelos de banco de dados, principalmente quando os dados possuem estruturas muito grandes, flexíveis, distribuídas ou altamente conectadas.

Os principais modelos além do relacional são:

  • Hierárquico
  • Em rede
  • Orientado a objetos
  • Chave-valor
  • Orientado a documentos
  • Orientado a colunas
  • Orientado a grafos
  • Multimodelo
  • Vetorial

1. Modelo Hierárquico

O modelo hierárquico organiza os dados em uma estrutura semelhante a uma árvore.

Cada elemento possui uma relação de hierarquia com outros elementos.

Empresa
│
├── Departamento
│   ├── Funcionário
│   └── Funcionário
│
└── Departamento
    ├── Funcionário
    └── Funcionário

Nesse modelo existe normalmente uma relação de:

Pai
 ↓
Filho

Características

  • Estrutura em árvore;
  • Organização hierárquica;
  • Navegação por caminhos;
  • Bom desempenho em estruturas naturalmente hierárquicas.

Vantagens

  • Estrutura simples;
  • Boa velocidade para determinados tipos de consulta;
  • Fácil representação de hierarquias.

Desvantagens

  • Pouca flexibilidade;
  • Relacionamentos complexos são difíceis;
  • Alterações na estrutura podem ser trabalhosas.

Exemplo de utilização

Pode ser adequado para estruturas como:

Empresa
 ↓
Departamento
 ↓
Funcionário

Esse modelo teve grande importância histórica no desenvolvimento dos bancos de dados.

2. Modelo em Rede

O modelo em rede surgiu como uma evolução do modelo hierárquico.

Enquanto o modelo hierárquico trabalha principalmente com uma estrutura de árvore, o modelo em rede permite relacionamentos mais complexos.

Aluno ─────── Curso A
  │             │
  │             │
  └────────── Curso B

Um registro pode estar relacionado a vários outros.

Vantagens

  • Mais flexível que o modelo hierárquico;
  • Permite relacionamentos complexos;
  • Bom desempenho em determinadas estruturas.

Desvantagens

  • Complexidade;
  • Difícil manutenção;
  • Menos utilizado atualmente.

Foi importante historicamente, mas perdeu espaço para o modelo relacional.

3. Banco de Dados Orientado a Objetos

O modelo orientado a objetos procura armazenar dados utilizando conceitos semelhantes aos da Programação Orientada a Objetos (POO).

Em vez de pensar apenas em tabelas, podemos pensar em objetos.

Exemplo:

Objeto Cliente
│
├── nome
├── CPF
├── endereço
│
└── métodos

O objeto pode possuir:

  • Atributos;
  • Comportamentos;
  • Identidade;
  • Relacionamentos.

Características

Pode trabalhar com conceitos como:

  • Classes;
  • Objetos;
  • Herança;
  • Encapsulamento;
  • Polimorfismo.

Vantagem

Existe uma maior aproximação entre a estrutura dos dados e aplicações desenvolvidas com orientação a objetos.

Desvantagem

Não possui a mesma popularidade dos bancos relacionais tradicionais.

4. Modelo Chave-Valor

O modelo chave-valor é um dos modelos NoSQL mais simples.

Os dados são armazenados como pares:

CHAVE → VALOR

Exemplo:

usuario:1001 → "João"
usuario:1002 → "Maria"
usuario:1003 → "Carlos"

O valor também pode ser mais complexo:

usuario:1001 →
{
    nome: "João",
    idade: 25,
    cidade: "Fortaleza"
}

Funcionamento

A aplicação fornece uma chave:

usuario:1001

O banco retorna o valor correspondente.

Vantagens

  • Muito rápido;
  • Simples;
  • Fácil de escalar;
  • Excelente para determinadas operações de leitura e escrita.

Desvantagens

  • Consultas complexas podem ser limitadas;
  • Não é ideal para relacionamentos complexos.

Exemplos

  • Redis
  • Amazon DynamoDB

5. Modelo Orientado a Documentos

Os bancos orientados a documentos armazenam informações como documentos.

Um formato muito comum é o JSON.

Exemplo:

{
    "id": 1,
    "nome": "João",
    "idade": 25,
    "cidade": "Fortaleza"
}

Outro documento poderia possuir uma estrutura diferente:

{
    "id": 2,
    "nome": "Maria",
    "email": "maria@email.com",
    "telefones": [
        "99999-1111",
        "98888-2222"
    ]
}

Observe que os documentos não precisam necessariamente possuir exatamente os mesmos campos.

Características

  • Estrutura flexível;
  • Documentos independentes;
  • Geralmente utiliza JSON ou formatos semelhantes;
  • Boa escalabilidade.

Vantagens

  • Flexibilidade;
  • Desenvolvimento rápido;
  • Boa adaptação a aplicações Web;
  • Facilidade para armazenar estruturas complexas.

Desvantagens

  • Relacionamentos complexos podem ser mais difíceis;
  • Pode ocorrer duplicação de informações;
  • Nem sempre é a melhor opção para dados altamente relacionais.

Exemplos

  • MongoDB
  • CouchDB
  • Amazon DocumentDB

6. Modelo Orientado a Colunas

Os bancos orientados a colunas armazenam e processam dados de maneira diferente dos bancos relacionais tradicionais.

Em um banco relacional, podemos imaginar:

ID | Nome | Cidade | Idade

Em determinados bancos colunares, os dados são organizados de maneira que o acesso por colunas seja extremamente eficiente.

Conceitualmente:

ID:
1
2
3

Nome:
João
Maria
Carlos

Cidade:
Fortaleza
Natal
Recife

Esse modelo é especialmente interessante para:

  • Big Data;
  • Analytics;
  • Grandes volumes de informações;
  • Processamento distribuído.

Exemplos

  • Apache Cassandra
  • Apache HBase
  • Google Bigtable

7. Modelo Orientado a Grafos

O modelo de grafos é utilizado quando os relacionamentos entre os dados são tão importantes quanto os próprios dados.

Os dados são representados principalmente por:

  • Nós (nodes)
  • Relacionamentos (edges)

Exemplo:

        amigo
João ─────────→ Maria
 │
 │ trabalha
 ↓
Empresa X

Outro exemplo:

João
 │
 ├── amigo → Maria
 │
 ├── mora → Fortaleza
 │
 └── trabalha → Empresa X

Onde é utilizado?

É especialmente útil para:

  • Redes sociais;
  • Sistemas de recomendação;
  • Detecção de fraudes;
  • Mapas;
  • Redes de relacionamento;
  • Análise de conexões;
  • Grafos de conhecimento.

Exemplo

Imagine uma rede social.

Para descobrir:

"Quais amigos de João também são amigos de Maria?"

Um banco de grafos pode ser muito eficiente para trabalhar com esse tipo de relacionamento.

Exemplos

  • Neo4j
  • Amazon Neptune
  • JanusGraph

8. Modelo Multimodelo

Os bancos multimodelo permitem trabalhar com diferentes modelos de dados dentro de uma mesma plataforma.

Um sistema pode trabalhar, por exemplo, com:

Documentos
    +
Grafos
    +
Chave-Valor

Isso pode ser útil quando uma aplicação possui necessidades diferentes.

Exemplo

Uma aplicação poderia armazenar:

Usuários → Documentos
Sessões → Chave-Valor
Relacionamentos → Grafos

Em vez de utilizar obrigatoriamente três sistemas diferentes, uma solução multimodelo pode centralizar essas estruturas.

9. Bancos de Dados Vetoriais

Os bancos vetoriais ganharam grande importância com a expansão das aplicações de Inteligência Artificial.

Eles armazenam representações numéricas chamadas vetores.

Por exemplo, um texto pode ser transformado em um vetor:

"Banco de dados"
       ↓
[0.21, -0.45, 0.78, 0.12, ...]

Esses vetores representam características semânticas dos dados.

O banco pode então procurar vetores semelhantes.

Pergunta
   ↓
Embedding
   ↓
Vetor
   ↓
Busca por similaridade
   ↓
Resultados semelhantes

Aplicações

  • IA generativa;
  • Busca semântica;
  • Sistemas de recomendação;
  • RAG (Retrieval-Augmented Generation);
  • Pesquisa de imagens;
  • Pesquisa de documentos.

Exemplos

  • Milvus
  • Qdrant
  • Weaviate
  • Pinecone

Uma das comparações mais importantes é entre os bancos relacionais e os NoSQL.

Exemplo:

Produtos

É muito adequado quando:

  • Os dados possuem estrutura bem definida;
  • Existem muitos relacionamentos;
  • Consistência transacional é importante;
  • SQL é conveniente para as consultas.

NoSQL

Pode utilizar:

  • A estrutura dos dados é flexível;

12. Os modelos não são necessariamente concorrentes

É importante entender que NoSQL não significa que os bancos relacionais ficaram ultrapassados.

Cada modelo resolve problemas diferentes.

Por exemplo:

Sistema bancário
       ↓
Banco Relacional

Enquanto:

Cache de aplicação
       ↓
Chave-Valor

E:

Rede social
       ↓
Banco de Grafos

E:

Aplicação de IA
       ↓
Banco Vetorial

Uma aplicação moderna pode até utilizar vários bancos simultaneamente.

14. Como escolher o modelo?

A escolha deve começar pelo problema, e não pela tecnologia.

Se você precisa de muitos relacionamentos e transações:

Relacional

Exemplo:

  • Banco;
  • ERP;
  • Sistema financeiro.

Se precisa de documentos flexíveis:

Documento

Exemplo:

  • Catálogo de produtos;
  • APIs;
  • Aplicações Web.

Se precisa de cache extremamente rápido:

Chave-valor

Exemplo:

  • Sessões;
  • Cache;
  • Contadores.

Se trabalha com relacionamentos complexos:

Grafos

Exemplo:

  • Redes sociais;
  • Fraudes;
  • Recomendações.

Se trabalha com grandes volumes analíticos:

Colunar

Exemplo:

  • Big Data;
  • Analytics.

Se trabalha com IA e busca semântica:

Vetorial

Exemplo:

  • RAG;
  • Busca por similaridade;
  • Sistemas de recomendação.

Resumo

Os SGBDs não se limitam ao modelo relacional. Ao longo da evolução dos bancos de dados, diferentes modelos foram desenvolvidos para atender necessidades específicas.

Os principais são:

  • Hierárquico — organiza dados em árvores.
  • Em rede — permite relacionamentos mais complexos.
  • Orientado a objetos — trabalha com objetos e conceitos de POO.
  • Chave-valor — armazena dados como pares chave/valor.
  • Orientado a documentos — utiliza documentos flexíveis, geralmente JSON.
  • Orientado a colunas — adequado para grandes volumes e análises.
  • Orientado a grafos — especializado em relacionamentos e conexões.
  • Multimodelo — combina diferentes modelos.
  • Vetorial — otimizado para similaridade e aplicações de Inteligência Artificial.

A principal ideia é:

Não existe um único modelo de banco de dados ideal para todos os problemas.

A escolha depende da estrutura dos dados, tipo de consulta, volume, velocidade, necessidade de relacionamentos, consistência, escalabilidade e finalidade da aplicação.
