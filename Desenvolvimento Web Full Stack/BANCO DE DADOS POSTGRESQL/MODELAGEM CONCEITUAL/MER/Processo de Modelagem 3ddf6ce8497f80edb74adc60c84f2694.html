Processo de Modelagem

Processo de Modelagem de Entidades e Relacionamentos

O processo de modelagem de entidades e relacionamentos é o conjunto de etapas utilizadas para transformar os requisitos de um sistema em uma representação estruturada dos dados que serão armazenados no banco de dados.

Esse processo normalmente utiliza o Modelo Entidade-Relacionamento (MER) e resulta em um Diagrama Entidade-Relacionamento (DER).

A ideia principal é responder:

Quais informações o sistema precisa armazenar e como essas informações estão relacionadas?

1. Levantamento dos requisitos

A primeira etapa é entender o funcionamento do sistema e identificar quais dados precisam ser armazenados.

Por exemplo, para um sistema de uma loja:

  • A loja possui clientes.
  • Clientes realizam pedidos.
  • Pedidos possuem produtos.
  • Um produto pode aparecer em vários pedidos.
  • Cada item do pedido possui uma quantidade.

Essas informações podem ser obtidas através de entrevistas, documentos, regras de negócio e análise do funcionamento da organização.

2. Identificação das entidades

Depois de entender os requisitos, identificamos os principais objetos ou conceitos sobre os quais o sistema precisa armazenar informações.

No exemplo da loja:

CLIENTE
PEDIDO
PRODUTO

Esses serão as entidades.

Uma boa pergunta para identificar entidades é:

"Sobre quais coisas precisamos guardar informações?"

Por exemplo:

CLIENTE → nome, CPF, e-mail...
PRODUTO → nome, preço, estoque...
PEDIDO → data, status, valor...

3. Identificação dos atributos

Depois de identificar as entidades, determinamos suas características, ou seja, seus atributos.

Por exemplo:

CLIENTE
├── id_cliente
├── nome
├── cpf
├── email
└── telefone
PRODUTO
├── id_produto
├── nome
├── preço
└── estoque
PEDIDO
├── id_pedido
├── data
└── status

Também precisamos identificar quais atributos serão responsáveis por identificar cada registro de forma única.

Exemplo:

id_cliente
id_produto
id_pedido

Esses atributos normalmente se transformarão em chaves primárias no modelo relacional.

4. Identificação dos relacionamentos

Agora precisamos descobrir como as entidades se relacionam.

No exemplo:

CLIENTE → realiza → PEDIDO

E:

PEDIDO → contém → PRODUTO

Os relacionamentos representam as associações existentes entre as entidades.

Podemos representar inicialmente:

CLIENTE ─── realiza ─── PEDIDO
PEDIDO ─── contém ─── PRODUTO

5. Definição das cardinalidades

Depois de identificar os relacionamentos, precisamos determinar quantas ocorrências de uma entidade podem estar relacionadas com outra.

As principais cardinalidades são:

1:1

Uma ocorrência de A está relacionada com uma ocorrência de B.

PESSOA 1 ───── 1 PASSAPORTE

1:N

Uma ocorrência de A pode estar relacionada com várias ocorrências de B.

CLIENTE 1 ───── N PEDIDO

Um cliente pode realizar vários pedidos, enquanto cada pedido pertence a um cliente.

N:N

Várias ocorrências de A podem estar relacionadas com várias ocorrências de B.

PEDIDO N ───── N PRODUTO

Um pedido possui vários produtos e um produto pode aparecer em vários pedidos.

6. Identificação de entidades associativas

Quando encontramos um relacionamento N:N, geralmente precisamos criar uma entidade associativa para representá-lo no modelo relacional.

No exemplo:

PEDIDO N ───── N PRODUTO

Criamos:

PEDIDO 1 ─── N ITEM_PEDIDO N ─── 1 PRODUTO

A entidade ITEM_PEDIDO pode possuir:

ITEM_PEDIDO
├── id_pedido
├── id_produto
├── quantidade
└── preço_unitário

Isso também permite armazenar informações que pertencem à própria relação entre pedido e produto.

7. Definição das regras de negócio

As regras de negócio são fundamentais para validar o modelo.

Por exemplo:

Um cliente pode realizar vários pedidos, mas cada pedido pertence a apenas um cliente.

Isso determina:

CLIENTE 1 ───── N PEDIDO

Outra regra:

Um pedido deve possuir pelo menos um produto.

Isso ajuda a definir as restrições do relacionamento.

As regras de negócio evitam criar um modelo que não corresponda ao funcionamento real do sistema.

8. Construção do DER

Com entidades, atributos, relacionamentos e cardinalidades definidos, podemos construir o Diagrama Entidade-Relacionamento.

Um exemplo simplificado:

┌──────────────┐
│   CLIENTE    │
├──────────────┤
│ id_cliente   │
│ nome         │
│ email        │
└───────┬──────┘
        │
        │ 1:N
        ▼
┌──────────────┐
│    PEDIDO    │
├──────────────┤
│ id_pedido    │
│ data         │
│ status       │
└───────┬──────┘
        │
        │ 1:N
        ▼
┌─────────────────┐
│   ITEM_PEDIDO   │
├─────────────────┤
│ id_pedido       │
│ id_produto      │
│ quantidade      │
│ preço_unitário  │
└────────┬────────┘
         │
         │ N:1
         ▼
┌──────────────┐
│   PRODUTO    │
├──────────────┤
│ id_produto   │
│ nome         │
│ preço        │
│ estoque      │
└──────────────┘

Esse modelo já apresenta uma visão bastante clara da estrutura dos dados.

9. Validação do modelo

Depois de criar o modelo, é necessário verificar se ele realmente representa os requisitos.

Devemos perguntar:

  • Todas as informações necessárias estão representadas?
  • Existem entidades desnecessárias?
  • Os atributos estão nas entidades corretas?
  • As cardinalidades estão corretas?
  • Existem relacionamentos N:N que precisam de entidades associativas?
  • As regras de negócio estão sendo respeitadas?
  • Existem informações duplicadas desnecessariamente?

Essa etapa é importante porque erros encontrados no modelo são muito mais fáceis de corrigir antes da implementação do banco.

10. Transformação para o modelo lógico

Depois que o modelo conceitual estiver definido, ele pode ser transformado em um modelo lógico.

Por exemplo:

CLIENTE
   ↓
tabela CLIENTE

PEDIDO
   ↓
tabela PEDIDO

PRODUTO
   ↓
tabela PRODUTO

ITEM_PEDIDO
   ↓
tabela ITEM_PEDIDO

Os relacionamentos passam a ser representados principalmente através de chaves estrangeiras (FOREIGN KEY).

Por exemplo:

PEDIDO
id_pedido
id_cliente  ← FK
data
status

E:

ITEM_PEDIDO
id_pedido   ← FK
id_produto  ← FK
quantidade
preco_unitario

11. Fluxo completo da modelagem

De forma resumida, o processo pode ser representado assim:

Levantamento de requisitos
          ↓
Identificação das entidades
          ↓
Identificação dos atributos
          ↓
Identificação dos relacionamentos
          ↓
Definição das cardinalidades
          ↓
Identificação de entidades associativas
          ↓
Definição das regras de negócio
          ↓
Construção do DER
          ↓
Validação do modelo
          ↓
Modelo lógico
          ↓
Modelo físico
          ↓
Implementação no SGBD

Exemplo completo

Imagine que o requisito seja:

"Uma escola possui vários alunos. Cada aluno pode estar matriculado em vários cursos. Cada curso possui vários alunos. A matrícula registra a data em que o aluno entrou no curso."

Entidades

ALUNO
CURSO
MATRÍCULA

Atributos

ALUNO
├── id_aluno
└── nome

CURSO
├── id_curso
└── nome

MATRÍCULA
├── id_aluno
├── id_curso
└── data_matricula

Relacionamentos

ALUNO N ─── N CURSO

Como é N:N, criamos:

ALUNO 1 ─── N MATRÍCULA N ─── 1 CURSO

Assim, o modelo representa tanto os dados dos alunos e cursos quanto a relação entre eles.

Resumo

O processo de modelagem de entidades e relacionamentos transforma os requisitos de um sistema em uma estrutura organizada para representar seus dados.

As principais etapas são:

  1. Levantar os requisitos
  1. Identificar entidades
  1. Definir atributos
  1. Identificar relacionamentos
  1. Definir cardinalidades
  1. Criar entidades associativas quando necessário
  1. Definir regras de negócio
  1. Construir o DER
  1. Validar o modelo
  1. Transformar em modelo lógico e posteriormente físico

O objetivo final é criar um modelo que represente de maneira correta, organizada e consistente os dados que o sistema precisa armazenar.
