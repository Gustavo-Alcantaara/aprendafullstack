Entidades e Relacionamentos

Diagrama Entidade-Relacionamento (DER)

O Diagrama Entidade-Relacionamento (DER) é uma representação gráfica utilizada para modelar a estrutura de um banco de dados.

Ele mostra principalmente:

  • Entidades;
  • Atributos;
  • Relacionamentos;
  • Cardinalidades.

O DER é normalmente construído durante o Projeto Conceitual do banco de dados.

Requisitos
    ↓
Projeto Conceitual
    ↓
DER
    ↓
Projeto Lógico
    ↓
Projeto Físico

1. Para que serve o DER?

O DER permite visualizar como as informações de um sistema estão organizadas e relacionadas antes de criar as tabelas no banco de dados.

Por exemplo, em um sistema de vendas:

Cliente → realiza → Pedido
Pedido  → contém → Produto

O diagrama ajuda a entender essas relações de maneira visual.

Principais objetivos:

  • Organizar os dados;
  • Identificar entidades;
  • Definir relacionamentos;
  • Identificar atributos;
  • Definir cardinalidades;
  • Detectar problemas no modelo antes da implementação.

2. Entidades

Uma entidade representa algo sobre o qual precisamos armazenar informações.

Exemplos:

CLIENTE
PRODUTO
PEDIDO
FUNCIONÁRIO
CATEGORIA

No DER, uma entidade normalmente é representada por um retângulo:

┌──────────────┐
│   CLIENTE    │
└──────────────┘

Podemos pensar em uma entidade como algo que posteriormente poderá se transformar em uma tabela no modelo relacional.

3. Atributos

Os atributos representam as características de uma entidade.

Por exemplo:

CLIENTE
├── id
├── nome
├── CPF
├── email
└── telefone

Eles descrevem as informações que queremos armazenar sobre cada cliente.

Exemplo:

Cliente
   │
   ├── id
   ├── nome
   ├── email
   └── telefone

4. Identificador

Uma entidade geralmente possui um atributo capaz de identificar cada ocorrência de maneira única.

Por exemplo:

CLIENTE
├── id ← identificador
├── nome
├── email
└── telefone

O id pode identificar cada cliente:

id | nome
---|------
1  | João
2  | Maria
3  | Carlos

No modelo relacional, esse identificador normalmente será utilizado como chave primária (PK).

5. Relacionamentos

Um relacionamento representa uma associação entre entidades.

Por exemplo:

CLIENTE ─── realiza ─── PEDIDO

Isso significa que existe uma relação entre clientes e pedidos.

Outro exemplo:

PEDIDO ─── contém ─── PRODUTO

Os relacionamentos são importantes porque os dados de um sistema geralmente não existem de forma isolada.

6. Cardinalidade

A cardinalidade indica quantas ocorrências de uma entidade podem estar associadas a outra.

As principais cardinalidades são:

  • 1:1 — um para um;
  • 1:N — um para muitos;
  • N:N — muitos para muitos.

6.1 Relacionamento 1:1

Um registro de uma entidade está relacionado a, no máximo, um registro de outra entidade.

Exemplo:

PESSOA 1 ───── 1 PASSAPORTE

Uma pessoa pode possuir um passaporte e, nesse modelo, cada passaporte pertence a uma única pessoa.

6.2 Relacionamento 1:N

É um dos relacionamentos mais comuns.

Exemplo:

CLIENTE 1 ───── N PEDIDO

Significa:

Um cliente pode realizar vários pedidos, mas cada pedido pertence a um único cliente.

Visualmente:

CLIENTE
   │
   │ 1
   │
   └────────── N
              PEDIDO

6.3 Relacionamento N:N

Também chamado de muitos para muitos.

Exemplo:

PEDIDO N ───── N PRODUTO

Significa:

Um pedido pode possuir vários produtos e um produto pode aparecer em vários pedidos.

No modelo relacional, esse relacionamento normalmente será convertido em uma entidade associativa, como ITEM_PEDIDO.

PEDIDO
   │
   │ 1:N
   ↓
ITEM_PEDIDO
   ↑
   │ N:1
   │
PRODUTO

7. Exemplo de DER de uma loja

Imagine um sistema de vendas.

Temos as entidades:

CLIENTE
PRODUTO
PEDIDO
ITEM_PEDIDO

Os relacionamentos podem ser:

CLIENTE 1 ───── N PEDIDO

PEDIDO 1 ───── N ITEM_PEDIDO

PRODUTO 1 ───── N ITEM_PEDIDO

Podemos representar:

┌──────────────┐
│   CLIENTE    │
├──────────────┤
│ id           │
│ nome         │
│ email        │
└──────┬───────┘
       │
       │ 1:N
       ↓
┌──────────────┐
│    PEDIDO    │
├──────────────┤
│ id           │
│ data         │
└──────┬───────┘
       │
       │ 1:N
       ↓
┌─────────────────┐
│   ITEM_PEDIDO   │
├─────────────────┤
│ pedido_id       │
│ produto_id      │
│ quantidade      │
└────────┬────────┘
         │
         │ N:1
         ↓
┌──────────────┐
│   PRODUTO    │
├──────────────┤
│ id           │
│ nome         │
│ preco        │
└──────────────┘

Esse modelo representa a estrutura básica do sistema de vendas.

8. DER × Modelo Entidade-Relacionamento

É importante diferenciar os termos.

Modelo Entidade-Relacionamento (MER)

É o modelo conceitual utilizado para representar entidades, atributos e relacionamentos.

Diagrama Entidade-Relacionamento (DER)

É a representação gráfica desse modelo.

De forma simples:

MER
↓
Modelo conceitual

DER
↓
Desenho/diagrama desse modelo

Na prática, porém, os termos MER e DER muitas vezes são utilizados de maneira intercambiável.

9. DER e banco de dados relacional

O DER não é necessariamente o banco de dados final.

Ele é uma etapa de planejamento.

Por exemplo:

DER

CLIENTE
   │
   │ 1:N
   ↓
PEDIDO

Modelo lógico

CLIENTES
├── id (PK)
├── nome
└── email

PEDIDOS
├── id (PK)
├── cliente_id (FK)
└── data

Implementação física

CREATE TABLE clientes (
    id SERIAL PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    email VARCHAR(150)
);

CREATE TABLE pedidos (
    id SERIAL PRIMARY KEY,
    cliente_id INTEGER NOT NULL,
    data DATE NOT NULL,

    FOREIGN KEY (cliente_id)
        REFERENCES clientes(id)
);

Assim:

DER
 ↓
Modelo Lógico
 ↓
SQL
 ↓
PostgreSQL

10. Importância das cardinalidades

Definir corretamente as cardinalidades é essencial.

Imagine:

CLIENTE 1 ───── N PEDIDO

Isso garante que o modelo representa corretamente a regra:

Um cliente pode fazer vários pedidos.

Se colocássemos:

CLIENTE 1 ───── 1 PEDIDO

estaríamos dizendo que cada cliente poderia ter apenas um pedido, o que provavelmente estaria errado para um sistema de vendas.

Por isso, a cardinalidade deve refletir as regras de negócio identificadas durante o levantamento de requisitos.

11. DER e regras de negócio

O DER deve representar as regras importantes do sistema.

Por exemplo:

"Uma disciplina pode possuir vários alunos e um aluno pode cursar várias disciplinas."

Temos:

ALUNO N ───── N DISCIPLINA

Como é N:N, no modelo relacional podemos criar:

ALUNO
   │
   ↓
MATRÍCULA
   ↑
   │
DISCIPLINA

A entidade MATRÍCULA pode possuir informações próprias:

MATRÍCULA
├── aluno_id
├── disciplina_id
├── data
└── nota

Isso mostra como o DER ajuda a descobrir quais estruturas serão necessárias no banco.

12. Ferramentas para criar DER

Existem várias ferramentas que podem ser utilizadas para criar diagramas de banco de dados, como:

  • pgAdmin, para trabalhar com PostgreSQL;
  • MySQL Workbench;
  • diagrams.net (draw.io);
  • Lucidchart;
  • ferramentas de modelagem específicas.

O importante não é apenas saber desenhar o diagrama, mas saber interpretar e construir corretamente o modelo.

13. Principais elementos do DER

ElementoFunção
EntidadeRepresenta algo do sistema
AtributoCaracterística da entidade
IdentificadorIdentifica uma ocorrência
RelacionamentoLiga entidades
CardinalidadeDefine quantidade de ocorrências
Entidade associativaResolve relacionamentos N:N

Resumo

O Diagrama Entidade-Relacionamento (DER) é uma ferramenta fundamental para o Projeto Conceitual de um banco de dados.

Ele permite visualizar:

ENTIDADES
    ↓
ATRIBUTOS
    ↓
RELACIONAMENTOS
    ↓
CARDINALIDADES

Um exemplo simples:

┌───────────┐        1:N        ┌───────────┐
│  CLIENTE  │───────────────────│   PEDIDO  │
└───────────┘                   └───────────┘
                                      │
                                      │ 1:N
                                      ↓
                                ┌─────────────┐
                                │ ITEM_PEDIDO │
                                └─────────────┘
                                      ↑
                                      │ N:1
                                      │
                                ┌───────────┐
                                │  PRODUTO  │
                                └───────────┘

Em resumo, o DER permite planejar visualmente a estrutura e os relacionamentos de um banco antes de sua implementação. Ele serve como uma ponte importante entre os requisitos do sistema e o modelo lógico do banco de dados.
