Projeto Lógico

Projeto Lógico de Banco de Dados

O Projeto Lógico é a etapa em que o modelo conceitual é transformado em uma estrutura adequada ao modelo de banco de dados escolhido, geralmente o modelo relacional.

Ele acontece depois do levantamento de requisitos e do projeto conceitual, e antes do projeto físico.

Levantamento de Requisitos
          ↓
Projeto Conceitual
          ↓
   Projeto Lógico
          ↓
   Projeto Físico
          ↓
Implementação no SGBD

1. Objetivo do Projeto Lógico

O objetivo principal é definir como os dados serão organizados logicamente no banco.

No modelo relacional, isso significa definir:

  • Tabelas;
  • Colunas;
  • Chaves primárias;
  • Chaves estrangeiras;
  • Relacionamentos;
  • Restrições;
  • Normalização;
  • Tipos de dados em nível lógico.

Ainda não estamos preocupados com detalhes específicos de armazenamento no disco ou configurações de hardware.

2. Transformação do modelo conceitual

Imagine que no projeto conceitual temos:

CLIENTE
   │
   │ 1:N
   ↓
PEDIDO

No projeto lógico, isso será transformado em tabelas:

CLIENTE
├── id
├── nome
└── email

PEDIDO
├── id
├── data
└── cliente_id

A coluna cliente_id será uma chave estrangeira que referencia CLIENTE.

3. Tabelas

No modelo relacional, cada entidade geralmente é transformada em uma tabela.

Exemplo:

Entidade:
CLIENTE

        ↓

Tabela:
CLIENTES

Podemos ter:

CREATE TABLE clientes (
    id INTEGER PRIMARY KEY,
    nome VARCHAR(100),
    email VARCHAR(150)
);

4. Chave Primária

A chave primária (Primary Key) identifica unicamente cada registro de uma tabela.

Exemplo:

CREATE TABLE clientes (
    id INTEGER PRIMARY KEY,
    nome VARCHAR(100)
);

Nesse caso:

id
1
2
3
4

Cada cliente possui um identificador único.

5. Chave Estrangeira

A chave estrangeira (Foreign Key) é utilizada para estabelecer relacionamentos entre tabelas.

Exemplo:

CREATE TABLE pedidos (
    id INTEGER PRIMARY KEY,
    data DATE,
    cliente_id INTEGER,

    FOREIGN KEY (cliente_id)
    REFERENCES clientes(id)
);

Temos:

CLIENTES
id
 ↓
 ↑
cliente_id
PEDIDOS

Isso representa o relacionamento entre clientes e pedidos.

6. Transformação de relacionamentos

Um dos pontos mais importantes do Projeto Lógico é transformar os relacionamentos do modelo conceitual em estruturas relacionais.

Relacionamento 1:N

Exemplo:

CLIENTE 1 ───── N PEDIDO

A chave primária de CLIENTE é colocada como chave estrangeira em PEDIDO:

CLIENTE
id
 ↑
 │
cliente_id
PEDIDO

7. Relacionamento N:N

Considere:

PEDIDO N ───── N PRODUTO

Um pedido pode possuir vários produtos e um produto pode estar em vários pedidos.

No modelo relacional, normalmente criamos uma tabela associativa:

PEDIDOS
   │
   ↓
ITENS_PEDIDO
   ↑
   │
PRODUTOS

Por exemplo:

PEDIDOS
├── id
└── data

PRODUTOS
├── id
├── nome
└── preco

ITENS_PEDIDO
├── pedido_id
├── produto_id
└── quantidade

A tabela itens_pedido resolve o relacionamento muitos-para-muitos.

8. Normalização

A normalização é uma técnica importante do Projeto Lógico.

Seu objetivo é organizar os dados para reduzir problemas como:

  • Redundância;
  • Duplicação;
  • Inconsistência;
  • Problemas de atualização.

Por exemplo, seria ruim armazenar:

PEDIDO
------------------------------------------------
id | cliente | telefone | produto | preço
------------------------------------------------
1  | João    | 9999...  | Mouse   | 50
2  | João    | 9999...  | Teclado | 100

O telefone do João aparece várias vezes.

Uma estrutura melhor seria:

CLIENTES
id | nome | telefone

PEDIDOS
id | cliente_id

PRODUTOS
id | nome | preço

ITENS_PEDIDO
pedido_id | produto_id

Assim, cada informação fica armazenada no lugar adequado.

9. Formas Normais

As principais formas normais estudadas são:

1ª Forma Normal (1FN)

Os atributos devem conter valores atômicos, evitando grupos repetitivos em uma mesma coluna.

2ª Forma Normal (2FN)

Além de estar na 1FN, os atributos devem depender da chave inteira, especialmente quando existe chave composta.

3ª Forma Normal (3FN)

Além de estar na 2FN, deve-se evitar dependências transitivas entre atributos não-chave.

Na prática, a normalização ajuda a construir estruturas mais organizadas e consistentes.

10. Restrições

O Projeto Lógico também define regras que os dados precisam obedecer.

Exemplos:

PRIMARY KEY
FOREIGN KEY
NOT NULL
UNIQUE
CHECK

Exemplo:

CREATE TABLE produtos (
    id INTEGER PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    preco NUMERIC(10,2) CHECK (preco >= 0)
);

Nesse caso:

  • PRIMARY KEY → identifica o produto;
  • NOT NULL → exige o nome;
  • CHECK → impede preço negativo.

13. Exemplo completo

Imagine uma loja.

Modelo conceitual:

CLIENTE
   │
   │ 1:N
   ↓
PEDIDO
   │
   │ N:N
   ↓
PRODUTO

Modelo lógico:

CLIENTES
├── id (PK)
├── nome
└── email

PEDIDOS
├── id (PK)
├── data
└── cliente_id (FK)

PRODUTOS
├── id (PK)
├── nome
└── preco

ITENS_PEDIDO
├── pedido_id (PK/FK)
├── produto_id (PK/FK)
└── quantidade

A estrutura fica:

CLIENTES
    │
    │ 1:N
    ↓
PEDIDOS
    │
    │ 1:N
    ↓
ITENS_PEDIDO
    ↑
    │ N:1
    │
PRODUTOS

Essa estrutura já está muito próxima de uma implementação real em PostgreSQL, MySQL ou outro SGBD relacional.

Resumo

O Projeto Lógico transforma o modelo conceitual em uma estrutura adequada ao modelo de banco escolhido.

Suas principais atividades são:

  • Transformar entidades em tabelas;
  • Transformar atributos em colunas;
  • Definir chaves primárias;
  • Definir chaves estrangeiras;
  • Resolver relacionamentos N:N;
  • Aplicar normalização;
  • Definir restrições de integridade;
  • Organizar a estrutura lógica do banco.

A sequência pode ser resumida assim:

REQUISITOS
    ↓
MODELO CONCEITUAL
    ↓
ENTIDADES + RELACIONAMENTOS
    ↓
PROJETO LÓGICO
    ↓
TABELAS + COLUNAS + PK + FK
    ↓
NORMALIZAÇÃO
    ↓
PROJETO FÍSICO

Em resumo, o Projeto Lógico é a ponte entre o modelo conceitual e a implementação do banco de dados.
