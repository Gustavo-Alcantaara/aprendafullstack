Projeto Físico

Projeto Físico de Banco de Dados

O Projeto Físico é a etapa em que o modelo lógico do banco de dados é transformado em uma implementação concreta em um SGBD, como PostgreSQL, MySQL ou SQL Server.

Ele define como os dados serão realmente armazenados, acessados e otimizados, levando em consideração desempenho, segurança, armazenamento e características específicas do SGBD.

A sequência é:

Levantamento de Requisitos
          ↓
Projeto Conceitual
          ↓
Projeto Lógico
          ↓
Projeto Físico
          ↓
Implementação no SGBD

1. Objetivo do Projeto Físico

O principal objetivo é fazer com que o banco de dados tenha uma implementação eficiente, segura e adequada ao ambiente em que será executado.

Enquanto o projeto lógico define:

"Quais tabelas e relacionamentos teremos?"

O projeto físico define:

"Como essas estruturas serão implementadas e otimizadas no SGBD?"

2. Principais atividades

O Projeto Físico envolve principalmente:

  • Escolha do SGBD;
  • Definição dos tipos de dados;
  • Criação das tabelas;
  • Criação de índices;
  • Definição de particionamento;
  • Configuração de armazenamento;
  • Otimização de consultas;
  • Controle de acesso;
  • Estratégias de backup;
  • Planejamento de desempenho.

3. Escolha do SGBD

Uma das primeiras decisões é escolher qual SGBD será utilizado.

Exemplos:

  • PostgreSQL;
  • MySQL;
  • Oracle Database;
  • SQL Server;
  • MariaDB.

A escolha depende de fatores como:

  • Tipo de aplicação;
  • Quantidade de dados;
  • Número de usuários;
  • Desempenho esperado;
  • Recursos necessários;
  • Custo;
  • Conhecimento da equipe.

No seu caso, por exemplo, podemos implementar o projeto lógico utilizando PostgreSQL.

4. Definição dos tipos de dados

No projeto físico são definidos os tipos de dados específicos que serão utilizados.

Por exemplo:

CREATE TABLE clientes (
    id INTEGER,
    nome VARCHAR(100),
    email VARCHAR(150),
    nascimento DATE
);

Aqui definimos:

id         → INTEGER
nome       → VARCHAR(100)
email      → VARCHAR(150)
nascimento → DATE

A escolha correta dos tipos ajuda a evitar desperdício de armazenamento e problemas de conversão.

5. Criação das tabelas

O modelo lógico:

CLIENTES
├── id
├── nome
└── email

pode ser implementado fisicamente:

CREATE TABLE clientes (
    id SERIAL PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE
);

Agora temos uma estrutura realmente criada no PostgreSQL.

6. Índices

Os índices são um dos elementos mais importantes do projeto físico.

Eles podem melhorar significativamente o desempenho das consultas.

Imagine uma tabela com milhões de clientes:

SELECT *
FROM clientes
WHERE email = 'joao@email.com';

Um índice sobre email pode tornar essa busca muito mais eficiente:

CREATE INDEX idx_clientes_email
ON clientes(email);

Porém, índices também possuem custos.

Eles:

  • Ocupam espaço;
  • Precisam ser atualizados quando os dados mudam;
  • Podem tornar operações de escrita mais pesadas.

Portanto, devem ser utilizados de maneira planejada.

7. Particionamento

Quando uma tabela possui uma quantidade muito grande de dados, pode ser interessante utilizar particionamento.

Uma tabela grande pode ser dividida logicamente em partes menores.

Por exemplo:

VENDAS
│
├── VENDAS_2024
├── VENDAS_2025
└── VENDAS_2026

Isso pode facilitar:

  • Gerenciamento;
  • Consultas;
  • Manutenção;
  • Exclusão de dados antigos;
  • Desempenho em determinados cenários.

8. Armazenamento

O projeto físico também considera onde e como os dados serão armazenados.

Pode envolver:

  • SSD;
  • HDD;
  • Servidores locais;
  • Máquinas virtuais;
  • Cloud;
  • Sistemas distribuídos.

Para aplicações que exigem alto desempenho, o armazenamento pode ser um fator crítico.

9. Otimização de consultas

Uma parte importante do projeto físico é garantir que as consultas sejam executadas de maneira eficiente.

Por exemplo:

SELECT *
FROM pedidos
WHERE cliente_id = 10;

Podemos analisar como o PostgreSQL executa essa consulta utilizando ferramentas como:

EXPLAIN

ou:

EXPLAIN ANALYZE

Esses comandos ajudam a identificar problemas de desempenho.

10. Segurança

O projeto físico também precisa considerar a segurança do banco.

Podemos definir:

  • Usuários;
  • Roles;
  • Permissões;
  • Autenticação;
  • Controle de acesso;
  • Criptografia;
  • Auditoria.

Por exemplo:

Administrador
    ↓
Acesso completo

Aplicação
    ↓
Acesso somente ao necessário

Usuário comum
    ↓
Acesso limitado

Um princípio importante é o menor privilégio: cada usuário ou aplicação deve possuir apenas as permissões necessárias para realizar sua função.

11. Backup e recuperação

O projeto físico também deve definir como os dados serão protegidos contra perdas.

É necessário planejar:

Banco de Dados
      ↓
Backup
      ↓
Armazenamento seguro
      ↓
Teste de recuperação

É importante não apenas realizar backups, mas também testar se eles realmente podem ser restaurados.

12. Alta disponibilidade

Para sistemas críticos, o projeto físico pode incluir mecanismos para reduzir o tempo de indisponibilidade.

Exemplo:

        Banco Principal
              │
       ┌──────┴──────┐
       ↓             ↓
   Réplica A      Réplica B

Dependendo da arquitetura, podem ser utilizados:

  • Replicação;
  • Clusters;
  • Failover;
  • Balanceamento;
  • Redundância.

13. Projeto lógico × Projeto físico

Essa diferença é muito importante.

Projeto LógicoProjeto Físico
Define a estrutura lógicaDefine a implementação
TabelasTabelas implementadas
ColunasTipos de dados específicos
PK e FKPK e FK implementadas
NormalizaçãoÍndices e otimizações
RelacionamentosImplementação no SGBD
Independente do SGBD em maior grauEspecífico do SGBD

Exemplo:

Projeto lógico

CLIENTES
├── id
├── nome
└── email

Projeto físico no PostgreSQL

CREATE TABLE clientes (
    id SERIAL PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE
);

CREATE INDEX idx_clientes_email
ON clientes(email);

14. Exemplo completo

Imagine que temos no modelo lógico:

CLIENTES
├── id (PK)
├── nome
└── email

PEDIDOS
├── id (PK)
├── cliente_id (FK)
└── data

No projeto físico em PostgreSQL:

CREATE TABLE clientes (
    id SERIAL PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    email VARCHAR(150) UNIQUE NOT NULL
);

CREATE TABLE pedidos (
    id SERIAL PRIMARY KEY,
    cliente_id INTEGER NOT NULL,
    data DATE NOT NULL,

    CONSTRAINT fk_pedido_cliente
        FOREIGN KEY (cliente_id)
        REFERENCES clientes(id)
);

Podemos então adicionar um índice:

CREATE INDEX idx_pedidos_cliente
ON pedidos(cliente_id);

Agora temos uma implementação concreta do modelo lógico.

15. Importância do Projeto Físico

Um banco pode estar logicamente correto, mas apresentar baixo desempenho se for mal implementado.

Por exemplo:

Modelo lógico correto
        ↓
Implementação ruim
        ↓
Consultas lentas
        ↓
Sistema com baixo desempenho

Por isso, o projeto físico é fundamental para transformar um modelo bem estruturado em um banco eficiente e adequado ao ambiente real.

Resumo

O Projeto Físico é a última etapa do planejamento antes da implementação efetiva do banco.

Ele define principalmente como o banco será implementado e otimizado no SGBD escolhido.

Suas principais atividades são:

  • Escolher o SGBD;
  • Definir tipos de dados;
  • Criar tabelas;
  • Criar índices;
  • Planejar particionamento;
  • Otimizar consultas;
  • Definir armazenamento;
  • Configurar segurança;
  • Planejar backup;
  • Planejar recuperação e alta disponibilidade.

A sequência completa fica:

REQUISITOS
    ↓
PROJETO CONCEITUAL
    ↓
PROJETO LÓGICO
    ↓
PROJETO FÍSICO
    ↓
IMPLEMENTAÇÃO
    ↓
BANCO DE DADOS FUNCIONANDO

Em resumo: o projeto conceitual define o que existe, o projeto lógico define como os dados serão estruturados e o projeto físico define como essa estrutura será implementada e otimizada no SGBD.
