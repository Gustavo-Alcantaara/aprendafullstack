Levantamento de Requisitos e Projeto Conceitual

No desenvolvimento de um banco de dados, duas etapas fundamentais são o Levantamento de Requisitos e o Projeto Conceitual.

Essas etapas acontecem antes da implementação do banco e têm como objetivo garantir que o sistema seja construído de acordo com as necessidades reais dos usuários e da organização.

Podemos representar o processo de forma simplificada:

Necessidade do sistema
        ↓
Levantamento de Requisitos
        ↓
Projeto Conceitual
        ↓
Projeto Lógico
        ↓
Projeto Físico
        ↓
Implementação do Banco

1. Levantamento de Requisitos

O Levantamento de Requisitos é o processo de identificar e documentar quais informações o sistema precisa armazenar e quais operações precisam ser realizadas sobre elas.

É uma das primeiras etapas do desenvolvimento.

O objetivo é entender:

  • O que o sistema deve fazer;
  • Quais dados precisam ser armazenados;
  • Quem utilizará o sistema;
  • Quais regras devem ser respeitadas;
  • Quais informações precisam ser produzidas.

2. Por que o levantamento de requisitos é importante?

Um banco de dados mal planejado pode apresentar problemas mesmo que tecnicamente esteja funcionando.

Por exemplo, imagine desenvolver um sistema de uma loja sem descobrir que:

  • Um cliente pode fazer vários pedidos;
  • Um pedido pode conter vários produtos;
  • Um produto pode pertencer a diferentes categorias;
  • O estoque precisa ser atualizado automaticamente.

Se essas necessidades não forem identificadas no início, será necessário modificar o banco posteriormente.

Por isso:

Quanto melhor forem entendidos os requisitos, maior será a chance de construir um banco de dados adequado ao sistema.

3. Técnicas de levantamento de requisitos

Existem várias formas de descobrir as necessidades dos usuários.

Entrevistas

Conversar diretamente com as pessoas que utilizarão o sistema.

Exemplo:

"Quais informações você precisa registrar quando um cliente realiza uma compra?"

Questionários

Úteis quando existem muitos usuários e é necessário coletar informações de várias pessoas.

Observação

O analista acompanha como os processos são realizados na prática.

Análise de documentos

São analisados documentos existentes, como:

  • Formulários;
  • Relatórios;
  • Notas fiscais;
  • Planilhas;
  • Registros antigos.

Reuniões

Os envolvidos discutem os processos e definem as necessidades do sistema.

4. Tipos de requisitos

Os requisitos podem ser classificados de diferentes formas.

Requisitos funcionais

Descrevem o que o sistema deve fazer.

Exemplos:

  • Cadastrar clientes;
  • Cadastrar produtos;
  • Registrar pedidos;
  • Consultar vendas;
  • Atualizar estoque;
  • Emitir relatórios.

Requisitos não funcionais

Descrevem características ou restrições do sistema.

Exemplos:

  • Segurança;
  • Desempenho;
  • Disponibilidade;
  • Confiabilidade;
  • Escalabilidade.

Exemplo:

"O sistema deve permitir que apenas administradores alterem os preços dos produtos."

5. Regras de negócio

Durante o levantamento também são identificadas as regras de negócio.

São regras que determinam como o sistema deve funcionar.

Exemplos:

  • Um cliente pode realizar vários pedidos.
  • Um pedido deve pertencer a um cliente.
  • Um pedido deve possuir pelo menos um produto.
  • Um produto não pode possuir preço negativo.
  • Apenas usuários autorizados podem excluir produtos.

Essas regras serão importantes na construção do modelo do banco.

6. Exemplo de levantamento de requisitos

Imagine que precisamos desenvolver um banco para uma loja.

Após conversar com os responsáveis, descobrimos:

Clientes

O sistema deve armazenar:

  • Código;
  • Nome;
  • CPF;
  • E-mail;
  • Telefone.

Produtos

Deve armazenar:

  • Código;
  • Nome;
  • Preço;
  • Estoque.

Pedidos

Deve armazenar:

  • Código;
  • Data;
  • Cliente;
  • Produtos;
  • Quantidades.

Regras

  • Um cliente pode realizar vários pedidos.
  • Um pedido pertence a apenas um cliente.
  • Um pedido pode possuir vários produtos.
  • Um produto pode aparecer em vários pedidos.

Essas informações serão utilizadas na próxima etapa.

7. Projeto Conceitual

O Projeto Conceitual transforma os requisitos levantados em uma representação estruturada dos dados e de seus relacionamentos, sem se preocupar ainda com detalhes específicos do SGBD.

O modelo mais utilizado nessa etapa é o Modelo Entidade-Relacionamento (MER).

Sua representação gráfica é normalmente chamada de Diagrama Entidade-Relacionamento (DER).

8. Entidades

Uma entidade representa algo sobre o qual o sistema precisa armazenar informações.

No exemplo da loja:

Cliente
Produto
Pedido

Podemos representar:

┌───────────┐
│  CLIENTE  │
└───────────┘

┌───────────┐
│  PRODUTO  │
└───────────┘

┌───────────┐
│  PEDIDO   │
└───────────┘

9. Atributos

Os atributos representam as características de uma entidade.

Por exemplo:

CLIENTE
├── id
├── nome
├── CPF
├── email
└── telefone

Para produto:

PRODUTO
├── id
├── nome
├── preço
└── estoque

10. Relacionamentos

Os relacionamentos representam as associações entre as entidades.

No exemplo:

CLIENTE ───── realiza ───── PEDIDO

E:

PEDIDO ───── contém ───── PRODUTO

Assim podemos representar:

CLIENTE
   │
   │ realiza
   ↓
 PEDIDO
   │
   │ contém
   ↓
 PRODUTO

11. Cardinalidade

A cardinalidade indica quantas ocorrências de uma entidade podem estar relacionadas com outra.

Por exemplo:

CLIENTE 1 ───────── N PEDIDO

Isso significa:

Um cliente pode realizar vários pedidos.

E:

PEDIDO N ───────── N PRODUTO

Isso significa:

Um pedido pode possuir vários produtos e um produto pode estar presente em vários pedidos.

Esse relacionamento N:N (muitos para muitos) posteriormente precisará ser transformado no modelo lógico, geralmente por meio de uma entidade/tabela associativa.

12. DER do exemplo

Um modelo conceitual simplificado seria:

┌──────────────┐
│   CLIENTE    │
├──────────────┤
│ id           │
│ nome         │
│ cpf          │
│ email        │
└──────┬───────┘
       │
       │ 1:N
       ↓
┌──────────────┐
│    PEDIDO    │
├──────────────┤
│ id           │
│ data         │
└──────┬───────┘
       │
       │ N:N
       ↓
┌──────────────┐
│   PRODUTO    │
├──────────────┤
│ id           │
│ nome         │
│ preco        │
│ estoque      │
└──────────────┘

Esse modelo ainda é conceitual. Não estamos preocupados, por exemplo, com comandos SQL ou com a estrutura física do PostgreSQL.

13. Diferença entre levantamento de requisitos e projeto conceitual

Levantamento de RequisitosProjeto Conceitual
Descobre as necessidadesOrganiza essas necessidades
Conversa com usuáriosCria o modelo dos dados
Identifica regras de negócioIdentifica entidades e relacionamentos
Define o que o sistema precisa fazerRepresenta como os dados se relacionam
É mais voltado ao negócioÉ mais voltado à estrutura dos dados

Podemos resumir:

LEVANTAMENTO
"Quais são as necessidades?"

        ↓

PROJETO CONCEITUAL
"Como podemos representar essas informações?"

14. Importância dessas etapas

Essas etapas são fundamentais porque evitam que o banco seja criado diretamente sem compreender o problema.

Um bom processo é:

1. Entender o problema
        ↓
2. Conversar com os usuários
        ↓
3. Identificar requisitos
        ↓
4. Identificar regras de negócio
        ↓
5. Identificar entidades
        ↓
6. Identificar atributos
        ↓
7. Identificar relacionamentos
        ↓
8. Definir cardinalidades
        ↓
9. Criar o modelo conceitual

Depois disso, o projeto pode avançar para o modelo lógico, onde o modelo conceitual é convertido para uma estrutura adequada ao modelo de banco escolhido, como o relacional.

Resumo

O Levantamento de Requisitos busca descobrir o que o sistema precisa fazer e quais dados precisa armazenar.

O Projeto Conceitual transforma essas informações em um modelo organizado, normalmente utilizando Entidades, Atributos, Relacionamentos e Cardinalidades através do Modelo Entidade-Relacionamento (MER).

REQUISITOS
    ↓
Entender o negócio
    ↓
ENTIDADES
    ↓
ATRIBUTOS
    ↓
RELACIONAMENTOS
    ↓
CARDINALIDADES
    ↓
MODELO CONCEITUAL (MER/DER)

Essas etapas são a base para construir um banco de dados correto, organizado e alinhado às necessidades do sistema.
