Protocolo HTTP

O HTTP (Hypertext Transfer Protocol), ou Protocolo de Transferência de Hipertexto, é um dos protocolos mais importantes da Internet e da Web.

Ele define como clientes e servidores web trocam informações.

Quando você acessa:

https://www.exemplo.com

o navegador utiliza protocolos da família HTTP para solicitar recursos ao servidor, como:

  • páginas HTML;
  • arquivos CSS;
  • JavaScript;
  • imagens;
  • vídeos;
  • dados de APIs;
  • arquivos;
  • informações em formato JSON.

De forma simplificada:

Navegador
    │
    │ Requisição HTTP
    ↓
Servidor Web
    │
    │ Resposta HTTP
    ↓
Navegador

1. O que significa HTTP?

HTTP = Hypertext Transfer Protocol

Em português:

Protocolo de Transferência de Hipertexto.

Ele foi criado para permitir a comunicação entre clientes e servidores na Web.

O funcionamento básico é baseado no modelo:

CLIENTE
   │
   │ Request
   ↓
SERVIDOR
   │
   │ Response
   ↓
CLIENTE

O cliente normalmente é um navegador ou uma aplicação.

O servidor pode ser:

  • Apache;
  • Nginx;
  • IIS;
  • Node.js;
  • servidores Java;
  • servidores PHP;
  • aplicações Python;
  • entre outros.

2. HTTP pertence a qual camada?

O HTTP pertence à camada de aplicação do modelo TCP/IP.

Uma comunicação web tradicional pode ser representada assim:

┌─────────────────────────┐
│ HTTP                    │ ← Aplicação
├─────────────────────────┤
│ TCP                     │ ← Transporte
├─────────────────────────┤
│ IP                      │ ← Rede
├─────────────────────────┤
│ Ethernet / Wi-Fi        │ ← Acesso à rede
└─────────────────────────┘

No caso de HTTPS:

HTTP
 ↓
TLS
 ↓
TCP
 ↓
IP
 ↓
Rede

E com HTTP/3:

HTTP/3
   ↓
 QUIC
   ↓
 UDP
   ↓
 IP

3. HTTP funciona com cliente e servidor

O modelo tradicional do HTTP é baseado em requisição e resposta.

Por exemplo, quando você acessa uma página:

Navegador
    │
    │ GET /index.html
    ↓
Servidor
    │
    │ 200 OK
    │ HTML
    ↓
Navegador

O navegador faz uma requisição.

O servidor processa essa requisição e retorna uma resposta.

4. O que é uma requisição HTTP?

Uma requisição HTTP contém informações que dizem ao servidor:

"O que eu quero e como estou fazendo essa solicitação?"

Um exemplo simplificado:

GET /index.html HTTP/1.1
Host: exemplo.com
Accept: text/html

Podemos dividir isso em partes.

5. Método HTTP

A primeira parte é o método HTTP.

No exemplo:

GET /index.html HTTP/1.1

O método é:

GET

Ele indica a intenção da requisição.

Os principais métodos são:

MétodoUso
GETBuscar dados
POSTEnviar/criar dados
PUTSubstituir/atualizar recurso
PATCHAtualizar parcialmente
DELETERemover recurso
HEADObter apenas informações dos headers
OPTIONSConsultar opções/capacidades

6. GET

O GET é utilizado principalmente para obter recursos.

Por exemplo:

GET /usuarios

Pode significar:

"Quero obter a lista de usuários."

Outro exemplo:

GET /produtos/15

Pode significar:

"Quero obter o produto 15."

No desenvolvimento web:

fetch('/api/produtos');

pode gerar uma requisição GET.

7. POST

O POST é utilizado para enviar dados ao servidor.

Por exemplo, criar um usuário:

POST /usuarios

Com dados:

{
  "nome": "Gusta",
  "email": "gusta@example.com"
}

O servidor recebe os dados e pode criar o recurso.

Por exemplo:

POST /usuarios
       ↓
Servidor
       ↓
Cria usuário
       ↓
201 Created

8. PUT

O PUT normalmente é utilizado para substituir ou atualizar um recurso.

Por exemplo:

PUT /usuarios/10

Com:

{
  "nome": "Gusta",
  "email": "novo@example.com"
}

A ideia é:

Recurso antigo
      ↓
    PUT
      ↓
Recurso atualizado/substituído

9. PATCH

O PATCH é utilizado para uma atualização parcial.

Por exemplo:

PATCH /usuarios/10

Enviando:

{
  "nome": "Gustavo"
}

Nesse caso, você pode alterar apenas o nome sem precisar enviar todos os dados do usuário.

10. DELETE

O DELETE é utilizado para solicitar a remoção de um recurso.

Por exemplo:

DELETE /usuarios/10

Conceitualmente:

Usuário 10
    ↓
DELETE
    ↓
Usuário removido

11. URL

Uma requisição HTTP geralmente possui uma URL.

Por exemplo:

https://www.exemplo.com/produtos/10?categoria=games

Podemos dividir:

https://
   ↓
protocolo

www.exemplo.com
   ↓
domínio

/produtos/10
   ↓
caminho

?categoria=games
   ↓
query string

12. HTTP e DNS

O HTTP trabalha junto com o DNS.

Quando você acessa:

https://www.exemplo.com

primeiro é necessário descobrir onde está o servidor.

O DNS pode realizar:

www.exemplo.com
       ↓
      DNS
       ↓
      IP

Depois o navegador consegue estabelecer a comunicação com o servidor.

Simplificando:

DOMÍNIO
   ↓
DNS
   ↓
IP
   ↓
HTTP/HTTPS
   ↓
SERVIDOR

13. Headers

Os headers (cabeçalhos) carregam informações adicionais sobre a requisição ou resposta.

Exemplo:

GET /produtos HTTP/1.1
Host: exemplo.com
Accept: application/json
Authorization: Bearer token

Alguns headers importantes:

Host

Indica o domínio/host solicitado.

Host: exemplo.com

Content-Type

Indica o tipo do conteúdo enviado.

Content-Type: application/json

Isso significa que o corpo contém JSON.

Content-Length

Indica o tamanho do conteúdo.

Content-Length: 125

Authorization

Pode transportar credenciais ou tokens de autenticação.

Authorization: Bearer <token>

User-Agent

Identifica informações sobre o cliente.

User-Agent: Mozilla/5.0 ...

Accept

Indica quais tipos de conteúdo o cliente aceita.

Accept: application/json

14. Corpo da requisição

Nem toda requisição precisa possuir um corpo.

GET normalmente não precisa.

Já POST, PUT e PATCH frequentemente possuem.

Por exemplo:

POST /usuarios HTTP/1.1
Content-Type: application/json

{
  "nome": "Gusta",
  "idade": 20
}

Temos:

Cabeçalho
   ↓
Content-Type: application/json

Corpo
   ↓
{
   "nome": "Gusta",
   "idade": 20
}

15. Resposta HTTP

Depois da requisição, o servidor envia uma resposta.

Exemplo:

HTTP/1.1 200 OK
Content-Type: application/json

{
  "nome": "Gusta",
  "idade": 20
}

Ela também possui:

  • status code;
  • headers;
  • corpo.

16. Status Codes

Os status codes indicam o resultado da requisição.

Eles são divididos em cinco categorias.

FaixaSignificado
1xxInformações
2xxSucesso
3xxRedirecionamento
4xxErro do cliente
5xxErro do servidor

17. Principais códigos 2xx

200 OK

A requisição foi processada com sucesso.

200 OK

É um dos códigos mais comuns.

201 Created

Um recurso foi criado.

Muito comum depois de:

POST /usuarios

Resposta:

201 Created

204 No Content

A operação foi realizada com sucesso, mas não há conteúdo para retornar.

Por exemplo:

DELETE /usuarios/10

Pode retornar:

204 No Content

18. Principais códigos 3xx

301 Moved Permanently

Indica que o recurso foi movido permanentemente.

302 Found

Indica um redirecionamento.

304 Not Modified

Indica que o recurso não foi alterado desde a versão que o cliente possui em cache.

Isso ajuda a economizar tráfego.

19. Principais códigos 4xx

São erros geralmente relacionados à requisição do cliente.

400 Bad Request

A requisição possui algum problema.

400 Bad Request

401 Unauthorized

A autenticação é necessária ou não foi fornecida corretamente.

401 Unauthorized

403 Forbidden

O servidor entendeu a requisição, mas não permite o acesso.

403 Forbidden

Uma diferença importante:

401 → falta/erro de autenticação
403 → acesso não permitido

404 Not Found

O recurso não foi encontrado.

404 Not Found

Exemplo:

GET /produto/999999

se esse produto não existir.

405 Method Not Allowed

O método HTTP utilizado não é permitido naquele endpoint.

Por exemplo:

POST /usuarios

quando determinado endpoint aceita apenas GET.

20. Principais códigos 5xx

São erros relacionados ao processamento no servidor.

500 Internal Server Error

Erro interno genérico.

500 Internal Server Error

502 Bad Gateway

Um servidor intermediário recebeu uma resposta inválida de outro servidor.

503 Service Unavailable

O serviço está temporariamente indisponível.

Imagine uma API:

https://api.ghostware.com/usuarios

O cliente faz:

GET /usuarios HTTP/1.1
Host: api.ghostware.com
Accept: application/json

O servidor responde:

HTTP/1.1 200 OK
Content-Type: application/json

[
  {
    "id": 1,
    "nome": "Gusta"
  },
  {
    "id": 2,
    "nome": "João"
  }
]

Fluxo:

Cliente
   │
   │ GET /usuarios
   ↓
API
   │
   │ consulta banco
   ↓
Banco de Dados
   │
   │ resultados
   ↓
API
   │
   │ JSON
   ↓
Cliente

Esse é um padrão muito comum em aplicações Full Stack.

22. HTTP é stateless

Uma característica importante do HTTP tradicional é ser stateless, ou seja, cada requisição é tratada independentemente por padrão.

Por exemplo:

Requisição 1
GET /produtos

Requisição 2
GET /usuarios

Requisição 3
GET /pedidos

O protocolo não exige que o servidor mantenha automaticamente todo o contexto das requisições anteriores.

Para criar estado de sessão, aplicações utilizam mecanismos como:

  • cookies;
  • sessões;
  • tokens;
  • JWT;
  • bancos de dados;
  • caches.

23. Cookies

Os cookies permitem que o servidor armazene pequenos dados associados ao navegador.

Por exemplo:

Set-Cookie: session_id=abc123

O navegador posteriormente pode enviar:

Cookie: session_id=abc123

Isso permite implementar funcionalidades como:

  • sessões de login;
  • preferências;
  • carrinhos;
  • identificação de sessão.

24. HTTP e APIs

HTTP é extremamente importante para APIs.

Uma API REST, por exemplo, pode utilizar:

GET     /usuarios
POST    /usuarios
GET     /usuarios/10
PUT     /usuarios/10
PATCH   /usuarios/10
DELETE  /usuarios/10

Isso cria uma interface organizada para o frontend conversar com o backend.

Por exemplo:

Frontend
   │
   │ HTTP
   ↓
Backend / API
   │
   ↓
Banco de Dados

25. HTTP e JSON

Atualmente, APIs web utilizam muito o JSON para transportar dados.

Exemplo:

{
  "id": 10,
  "nome": "Gusta",
  "email": "gusta@example.com"
}

O HTTP transporta esse conteúdo.

HTTP
 ├── Método
 ├── URL
 ├── Headers
 └── Body
       ↓
      JSON

É importante entender:

JSON não é um protocolo de comunicação.

JSON é um formato de dados.

HTTP é o protocolo que pode transportar esses dados.

26. HTTP/1.0

Uma das primeiras versões amplamente utilizadas foi o HTTP/1.0.

Cada requisição normalmente utilizava uma conexão separada.

Conceitualmente:

Conexão
 ↓
Requisição
 ↓
Resposta
 ↓
Conexão encerrada

Isso gerava overhead.

27. HTTP/1.1

O HTTP/1.1 trouxe várias melhorias importantes.

Uma delas foi o suporte a conexões persistentes.

Em vez de criar uma nova conexão para cada requisição:

Conexão 1 → requisição 1
Conexão 2 → requisição 2
Conexão 3 → requisição 3

podemos reutilizar uma conexão:

Conexão
 ├── requisição 1
 ├── requisição 2
 ├── requisição 3
 └── requisição 4

O HTTP/1.1 também popularizou o uso do header:

Host:

28. HTTP/2

O HTTP/2 trouxe melhorias importantes de desempenho.

Entre elas está o conceito de multiplexação.

Em vez de tratar várias requisições como fluxos completamente independentes em conexões separadas, várias delas podem ser transportadas simultaneamente através de uma mesma conexão TCP.

Conceitualmente:

Uma conexão TCP
      │
      ├── Requisição A
      ├── Requisição B
      ├── Requisição C
      └── Requisição D

Isso pode reduzir overhead e melhorar o desempenho.

HTTP/2 também utiliza uma representação binária das mensagens, em vez do formato textual característico do HTTP/1.x.

29. HTTP/3

O HTTP/3 é uma evolução importante.

Em vez de utilizar TCP diretamente, ele utiliza QUIC, que funciona sobre UDP.

HTTP/3
   ↓
 QUIC
   ↓
 UDP
   ↓
 IP

O QUIC fornece mecanismos modernos de transporte, incluindo confiabilidade e controle de fluxo, enquanto aproveita UDP como base.

Portanto, não significa que:

"HTTP/3 não é confiável porque usa UDP."

A confiabilidade é fornecida pelo QUIC, não pelo UDP.

30. HTTP x HTTPS

Essa é uma diferença fundamental.

HTTP

HTTP
 ↓
TCP
 ↓
IP

HTTPS

HTTPS significa, essencialmente, HTTP protegido por TLS.

HTTP
 ↓
TLS
 ↓
TCP
 ↓
IP

O TLS fornece mecanismos de:

  • criptografia;
  • autenticação do servidor;
  • integridade dos dados.

Por isso, em aplicações modernas, o HTTPS é essencial.

31. HTTP não é criptografado

O HTTP tradicional não fornece criptografia.

Imagine:

Cliente
   │
   │ HTTP
   ↓
Rede
   ↓
Servidor

Os dados podem ser observáveis ou manipuláveis por um atacante que consiga interceptar o tráfego em determinadas condições.

Com HTTPS:

Cliente
   │
   │ HTTPS
   ↓
  TLS
   ↓
Rede
   ↓
Servidor

Os dados da aplicação são protegidos pelo TLS durante o transporte.

32. HTTP e segurança

Como HTTP é fundamental para aplicações web, ele está diretamente relacionado à Cibersegurança.

Alguns problemas de segurança podem envolver:

  • autenticação inadequada;
  • autorização incorreta;
  • exposição de informações;
  • ausência de HTTPS;
  • configuração incorreta de headers;
  • injeção;
  • XSS;
  • CSRF;
  • controle de acesso;
  • gerenciamento inadequado de sessão;
  • validação insuficiente de entrada.

Por isso, compreender HTTP é fundamental para entender segurança web.

33. Headers de segurança

Existem headers HTTP utilizados para melhorar a segurança.

Por exemplo:

Content-Security-Policy

Content-Security-Policy: ...

Ajuda a controlar quais recursos podem ser carregados pela página.

Strict-Transport-Security

Strict-Transport-Security: max-age=...

É utilizado para instruir o navegador a preferir HTTPS para determinado domínio.

X-Content-Type-Options

X-Content-Type-Options: nosniff

Ajuda a reduzir determinados comportamentos de interpretação indevida de tipos de conteúdo.

34. HTTP e portas

O HTTP tradicional utiliza:

TCP 80

O HTTPS tradicionalmente utiliza:

TCP 443

Já HTTP/3 utiliza:

UDP 443

através do QUIC.

Podemos resumir:

HTTP/1.1 → TCP 80
HTTPS    → TCP 443
HTTP/2   → normalmente TCP 443 + TLS
HTTP/3   → UDP 443 + QUIC

Vamos juntar tudo que você estudou até agora.

Imagine:

www.ghostware.com
        ↓
       DNS
        ↓
       IP

2. Transporte

Dependendo da versão:

HTTPS → TCP

ou:

HTTP/3 → QUIC → UDP

3. TLS

No HTTPS tradicional:

TCP
 ↓
TLS

O cliente e o servidor estabelecem uma comunicação protegida.

4. HTTP

O navegador envia:

GET / HTTP/1.1
Host: www.ghostware.com

5. Servidor

O servidor processa a requisição.

6. Resposta

Pode retornar:

HTTP/1.1 200 OK
Content-Type: text/html

seguido pelo HTML.

7. Navegador

O navegador interpreta o HTML e pode fazer novas requisições:

HTML
 ↓

 ↓
JavaScript
 ↓

 ↓
APIs
