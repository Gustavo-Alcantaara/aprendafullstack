Falhas Criptográficas

As Falhas Criptográficas são vulnerabilidades que acontecem quando uma aplicação protege informações de maneira inadequada usando criptografia, ou quando deveria utilizar mecanismos criptográficos e não os utiliza corretamente.

Esse tipo de problema pode expor informações que deveriam permanecer:

  • confidenciais;
  • íntegras;
  • autênticas;
  • protegidas contra acesso não autorizado.

Em aplicações web, isso pode envolver desde senhas e dados pessoais até informações financeiras, tokens de autenticação e comunicações entre cliente e servidor.

1. O que é criptografia?

A criptografia é um conjunto de técnicas utilizadas para proteger informações.

De forma simplificada:

Informação original
       ↓
   Criptografia
       ↓
Informação protegida
       ↓
   Descriptografia
       ↓
Informação original

Por exemplo:

Mensagem:
"Minha senha é 123456"

Depois de protegida criptograficamente, ela não deve permanecer legível para alguém que consiga interceptar ou acessar o conteúdo protegido.

O objetivo é impedir que pessoas não autorizadas consigam compreender ou modificar determinados dados.

2. O que as aplicações precisam proteger?

A criptografia pode ajudar a proteger diferentes propriedades.

Confidencialidade

Impede que pessoas não autorizadas leiam a informação.

Exemplo:

Usuário → HTTPS → Servidor

A comunicação é protegida contra interceptação simples.

Integridade

Permite detectar alterações indevidas nos dados.

Por exemplo:

Mensagem original
       ↓
   Integridade
       ↓
Mensagem alterada?

Se houver alteração, mecanismos apropriados podem detectar o problema.

Autenticidade

Ajuda a verificar se uma informação ou comunicação realmente veio da origem esperada.

Certificados digitais e assinaturas digitais são exemplos de mecanismos relacionados a isso.

3. O que caracteriza uma falha criptográfica?

Uma falha pode acontecer quando a aplicação:

  • não utiliza criptografia onde deveria;
  • utiliza algoritmos obsoletos;
  • utiliza chaves fracas;
  • armazena chaves de maneira insegura;
  • utiliza senhas de maneira inadequada;
  • utiliza configurações inseguras;
  • protege apenas parte da comunicação;
  • utiliza criptografia sem autenticação adequada;
  • armazena dados sensíveis em texto puro;
  • utiliza números aleatórios previsíveis;
  • não protege adequadamente os certificados;
  • utiliza criptografia própria ou improvisada.

Portanto, não é simplesmente:

"Não usar criptografia."

Uma implementação criptográfica mal configurada ou mal utilizada também pode ser vulnerável.

4. Dados sensíveis e criptografia

Aplicações normalmente trabalham com informações que precisam de proteção.

Por exemplo:

Nome
CPF
E-mail
Endereço
Dados financeiros
Documentos
Tokens
Informações médicas
Dados empresariais

A necessidade de proteção depende do tipo de informação e do contexto.

Uma aplicação deve identificar quais dados são realmente sensíveis e determinar como eles devem ser protegidos.

5. Criptografia em trânsito

Uma das aplicações mais comuns é proteger informações enquanto elas estão sendo transmitidas.

Por exemplo:

Navegador
    │
    │ HTTPS
    ▼
Servidor

O HTTPS utiliza TLS (Transport Layer Security) para proteger a comunicação.

Isso ajuda a proteger contra determinados tipos de interceptação e manipulação da comunicação.

6. HTTP × HTTPS

Uma forma simples de visualizar:

HTTP

Navegador
    │
    │ comunicação sem TLS
    ▼
Servidor

HTTPS

Navegador
    │
    │ comunicação protegida por TLS
    ▼
Servidor

Por isso, aplicações que trabalham com informações sensíveis devem utilizar HTTPS corretamente.

7. Criptografia em repouso

Também existe a proteção de dados armazenados.

Por exemplo:

Banco de dados
      ↓
Dados armazenados

A organização pode utilizar mecanismos de criptografia para proteger determinados dados em:

  • bancos;
  • discos;
  • backups;
  • dispositivos;
  • armazenamento em nuvem;
  • arquivos.

Isso é conhecido como proteção em repouso (data at rest).

8. Senhas não devem ser simplesmente criptografadas

Esse é um ponto muito importante.

Senhas de usuários não devem ser armazenadas simplesmente como texto puro:

usuario | senha
Gusta   | 123456

Mas também não é adequado tratar senha como um dado comum que precisa ser recuperado posteriormente.

Para senhas, normalmente utiliza-se uma função de hash específica para senhas.

Exemplos modernos incluem:

  • Argon2;
  • bcrypt;
  • scrypt;
  • PBKDF2.

9. Hash não é a mesma coisa que criptografia

Essa diferença é fundamental.

Criptografia

É projetada para permitir que o dado seja recuperado mediante a chave apropriada.

Dado
 ↓
Criptografia
 ↓
Dado protegido
 ↓
Descriptografia
 ↓
Dado original

Hash

É uma transformação de mão única.

Dado
 ↓
Hash
 ↓
Resultado

Não existe uma operação normal de "deshash" que simplesmente recupere a senha original.

Por isso, hashes apropriados são utilizados para armazenamento de senhas.

10. Salt

Além do algoritmo de hash adequado, senhas devem utilizar um salt.

O salt é um valor adicional associado à senha antes do processamento.

Conceitualmente:

Senha
  +
Salt
  ↓
Função de derivação/hash
  ↓
Resultado armazenado

Isso ajuda a impedir que senhas iguais produzam simplesmente o mesmo resultado e dificulta determinados ataques baseados em tabelas pré-computadas.

Bibliotecas modernas de armazenamento de senha normalmente cuidam do salt automaticamente.

11. Algoritmos criptográficos obsoletos

Outra fonte de falhas é utilizar algoritmos considerados inadequados para determinado objetivo.

Exemplos históricos incluem:

  • DES;
  • 3DES em novos projetos;
  • RC4;
  • MD5 para segurança criptográfica;
  • SHA-1 para determinados usos de segurança.

Isso não significa que todos possuem exatamente o mesmo nível ou tipo de problema. O ponto é que algoritmos e protocolos precisam ser escolhidos de acordo com seu uso e com as recomendações atuais.

Para novos sistemas, deve-se utilizar algoritmos e bibliotecas criptográficas modernas e mantidas.

12. Criptografia fraca

Mesmo um algoritmo adequado pode ser utilizado de maneira inadequada.

Por exemplo:

Algoritmo adequado
       +
Chave inadequada
       ↓
Proteção comprometida

A segurança depende de fatores como:

  • algoritmo;
  • tamanho da chave;
  • geração da chave;
  • armazenamento;
  • gerenciamento;
  • modo de operação;
  • implementação;
  • configuração.

Por isso, simplesmente dizer:

"O sistema usa AES"

não é suficiente para concluir que ele está seguro.

13. Gerenciamento de chaves

Um dos maiores desafios da criptografia não é apenas criptografar.

É proteger as chaves.

Imagine:

Dados criptografados
       ↓
Chave secreta

Se um atacante consegue obter a chave, a proteção pode perder grande parte de seu propósito.

As chaves devem ser armazenadas com cuidado, evitando:

❌ código-fonte
❌ repositório Git
❌ arquivos públicos
❌ mensagens
❌ comentários
❌ banco sem proteção adequada

Em ambientes profissionais, podem ser utilizados mecanismos como:

  • secret managers;
  • sistemas de gerenciamento de chaves;
  • HSMs;
  • variáveis de ambiente, quando adequadas;
  • controles de acesso;
  • rotação de chaves.

14. Nunca colocar chaves diretamente no código

Um exemplo problemático seria:

$key = "minha-chave-secreta";

dentro do código que será enviado para um repositório.

Se esse código for exposto:

Código
  ↓
Chave
  ↓
Atacante
  ↓
Dados potencialmente comprometidos

É preferível utilizar mecanismos apropriados de gerenciamento de segredos.

15. Criptografia própria

Um erro muito comum é tentar criar um algoritmo criptográfico próprio.

Por exemplo:

"Vou criar meu próprio sistema de criptografia."

Isso é extremamente arriscado.

Criptografia moderna depende de matemática, análise criptográfica e implementação cuidadosa.

Em aplicações reais, normalmente devemos utilizar:

  • bibliotecas consolidadas;
  • APIs criptográficas da linguagem;
  • protocolos padronizados;
  • algoritmos amplamente analisados.

Em segurança:

Não invente sua própria criptografia quando uma solução criptográfica estabelecida já existe.

16. Números aleatórios previsíveis

Sistemas criptográficos frequentemente precisam de valores aleatórios ou imprevisíveis.

Por exemplo:

  • tokens;
  • salts;
  • nonces;
  • chaves;
  • códigos temporários.

Utilizar um gerador de números aleatórios inadequado pode comprometer a segurança.

Por isso existem mecanismos específicos de aleatoriedade criptograficamente segura (CSPRNG).

17. Nonce e IV

Alguns algoritmos utilizam valores como:

  • IV — Initialization Vector
  • Nonce

Eles ajudam a tornar as operações criptográficas seguras e/ou impedir determinados padrões previsíveis.

Um erro de implementação pode comprometer a segurança mesmo quando o algoritmo utilizado é considerado seguro.

Isso mostra novamente:

Algoritmo seguro
       ≠
Implementação automaticamente segura

18. Criptografia sem autenticação

Outro problema é proteger apenas a confidencialidade sem garantir adequadamente a integridade/autenticidade.

Imagine:

Mensagem
   ↓
Criptografada
   ↓
Interceptada
   ↓
Alterada

Se o protocolo não tiver mecanismos apropriados para detectar essa alteração, o receptor poderá ter problemas.

Por isso, sistemas modernos frequentemente utilizam mecanismos de Authenticated Encryption, como famílias baseadas em:

  • AES-GCM;
  • ChaCha20-Poly1305.

O objetivo é proteger tanto o conteúdo quanto sua autenticidade/integridade dentro do modelo apropriado.

19. Certificados digitais

Em conexões HTTPS, os certificados digitais desempenham um papel importante.

Eles ajudam o cliente a verificar a identidade do servidor dentro da infraestrutura de confiança do TLS.

Simplificando:

Navegador
    ↓
Servidor
    ↓
Certificado
    ↓
Verificação
    ↓
Conexão TLS

Problemas com certificados, validação ou configuração do TLS podem comprometer a segurança da comunicação.

20. TLS antigo ou mal configurado

Não basta simplesmente ativar HTTPS.

Também é necessário utilizar configurações adequadas de TLS.

Uma configuração insegura pode envolver:

  • protocolos antigos;
  • cifras inadequadas;
  • certificados inválidos;
  • configurações incorretas;
  • falta de atualização;
  • validação inadequada.

Portanto:

HTTPS
   +
TLS corretamente configurado

é mais importante do que simplesmente observar um cadeado no navegador.

21. Dados criptografados e logs

Um erro interessante ocorre quando a aplicação protege os dados no banco, mas depois os coloca em logs sem proteção.

Por exemplo:

Banco:
senha/token → protegido

Log:
"token=abc123..."

Nesse cenário, o mecanismo de proteção pode ser contornado pelo próprio sistema de registros.

Por isso, é necessário considerar:

Banco
Backups
Logs
Caches
Arquivos temporários
Mensagens
Filas

ao definir a estratégia de proteção de dados.

22. Backups também precisam de proteção

Imagine:

Banco principal → criptografado

mas:

Backup → texto puro

Um atacante que obtenha o backup pode acessar os dados.

Portanto, dados sensíveis precisam ser protegidos também em:

  • backups;
  • snapshots;
  • dispositivos;
  • armazenamento externo;
  • ambientes de desenvolvimento;
  • ambientes de teste.

23. Exemplo em uma aplicação web

Imagine um sistema de comércio eletrônico:

                USUÁRIO
                   │
                   ▼
              NAVEGADOR
                   │
                 HTTPS
                   │
                   ▼
                BACKEND

A proteção criptográfica pode aparecer em várias partes:

Navegador ↔ Backend
       → TLS

Banco

Senhas
       → Argon2/bcrypt/etc.

Tokens/chaves
       → gerenciamento seguro de segredos

Backups
       → proteção adequada

24. Como prevenir falhas criptográficas?

Uma estratégia de segurança pode incluir:

1. Identificar dados sensíveis

Descobrir quais informações realmente precisam de proteção.

2. Utilizar criptografia apropriada

Escolher algoritmos e protocolos modernos e adequados ao objetivo.

3. Utilizar HTTPS/TLS

Principalmente em aplicações web que transportam informações sensíveis.

4. Armazenar senhas corretamente

Utilizar algoritmos específicos para senhas, como:

Argon2
bcrypt
scrypt
PBKDF2

5. Proteger as chaves

Não deixar chaves expostas no código ou repositórios.

6. Utilizar bibliotecas confiáveis

Não implementar primitivas criptográficas manualmente sem necessidade.

7. Utilizar aleatoriedade segura

Tokens, salts, nonces e chaves precisam ser gerados adequadamente.

8. Atualizar protocolos e bibliotecas

Evitar tecnologias criptográficas obsoletas.

9. Proteger backups

Não adianta proteger somente o banco de produção.

10. Não expor dados sensíveis em logs

Logs também fazem parte da superfície de ataque.

26. Principais erros para memorizar

Para estudar Segurança Cibernética, associe Falhas Criptográficas principalmente a:

❌ Dados sensíveis sem proteção
❌ Senhas em texto puro
❌ Hash inadequado para senhas
❌ Algoritmos obsoletos
❌ Chaves fracas
❌ Chaves expostas
❌ Criptografia mal configurada
❌ TLS mal configurado
❌ Números aleatórios previsíveis
❌ Criptografia desenvolvida "na mão"
❌ Backups sem proteção
❌ Dados sensíveis em logs

27. Resumo

Falhas Criptográficas acontecem quando mecanismos criptográficos são ausentes, fracos, obsoletos, mal configurados ou utilizados incorretamente.

Os principais conceitos são:

ConceitoObjetivo
CriptografiaProteger dados recuperáveis com uma chave
HashTransformação de mão única
SaltAumentar a resistência do armazenamento de senhas
TLSProteger comunicação
HTTPSHTTP sobre TLS
Chave criptográficaControlar operações criptográficas
Certificado digitalAuxiliar na autenticação de entidades
Assinatura digitalAutenticidade e integridade
CSPRNGGerar valores imprevisíveis
KDFDerivar chaves/armazenar credenciais de forma apropriada

A ideia principal é:

                 DADOS SENSÍVEIS
                       │
           ┌───────────┴───────────┐
           ▼                       ▼
      EM TRÂNSITO              ARMAZENADOS
           │                       │
         TLS                 Criptografia
           │                       │
           └───────────┬───────────┘
                       ▼
               CHAVES PROTEGIDAS
                       │
                       ▼
              IMPLEMENTAÇÃO SEGURA

Criptografia não é apenas escolher um algoritmo. É necessário escolher o mecanismo correto para cada finalidade, proteger as chaves, utilizar implementações confiáveis, configurar os protocolos corretamente e proteger todo o ciclo de vida dos dados.
