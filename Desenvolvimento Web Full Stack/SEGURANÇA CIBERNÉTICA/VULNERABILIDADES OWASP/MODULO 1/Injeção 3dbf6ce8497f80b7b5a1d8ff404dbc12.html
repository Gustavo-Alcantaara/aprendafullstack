Injeção

No contexto de Segurança Cibernética, injeção (Injection) é uma categoria de vulnerabilidade em que dados fornecidos pelo usuário são interpretados pelo sistema como parte de um comando, consulta ou código, em vez de serem tratados apenas como dados.

É uma das classes de vulnerabilidades mais importantes em aplicações web porque pode permitir que um atacante faça a aplicação executar operações que não deveriam ser permitidas.

1. O que é uma vulnerabilidade de injeção?

Imagine uma aplicação que recebe uma informação do usuário e depois monta uma instrução utilizando essa informação.

O problema acontece quando a aplicação mistura dados com comandos, sem realizar uma validação ou parametrização adequada.

De forma simplificada:

Entrada do usuário
       ↓
Aplicação
       ↓
Comando/consulta
       ↓
Sistema interpreta

Se a aplicação não separar corretamente dados de instruções, uma entrada maliciosa pode alterar o comportamento esperado.

Exemplo conceitual

Uma aplicação deveria receber:

nome = Gustavo

e produzir uma consulta baseada nesse nome.

Porém, se o sistema simplesmente juntar textos para construir a consulta, uma entrada especialmente preparada pode modificar a estrutura da consulta.

O princípio é:

Dado legítimo → tratado como dado
Entrada maliciosa → pode ser interpretada como comando

2. Por que a injeção acontece?

A causa principal costuma ser a falta de separação entre dados e comandos.

Alguns fatores comuns são:

  • construção manual de consultas;
  • concatenação de strings;
  • falta de validação de entrada;
  • falta de parametrização;
  • utilização insegura de comandos do sistema;
  • APIs mal projetadas;
  • tratamento inadequado de dados recebidos do usuário;
  • utilização de bibliotecas ou funções inseguras;
  • falta de controle sobre os tipos de dados esperados.

Um exemplo conceitual:

"SELECT ... WHERE nome = '" + entrada + "'"

Aqui existe uma mistura direta entre:

comando SQL
+
dados fornecidos pelo usuário

Essa abordagem pode criar uma vulnerabilidade.

Existem vários tipos de ataques de injeção.

Os mais importantes para aplicações web são:

TipoAlvo
SQL InjectionBanco de dados SQL
NoSQL InjectionBancos NoSQL
Command InjectionSistema operacional
OS Command InjectionComandos do sistema
LDAP InjectionServidores LDAP

Cada um explora um mecanismo diferente, mas o princípio geral é semelhante:

Uma entrada controlada pelo usuário acaba sendo interpretada como uma instrução.

4. SQL Injection

Um dos exemplos mais conhecidos é o SQL Injection.

Ele acontece quando uma aplicação constrói consultas SQL de maneira insegura.

Imagine uma aplicação de login:

Usuário: Gustavo
Senha: ********

O sistema precisa consultar o banco:

SELECT * FROM usuarios
WHERE usuario = ...
AND senha = ...;

Se os valores forem inseridos diretamente na string da consulta, um atacante pode tentar fornecer uma entrada que altere a lógica da consulta.

Consequências

Dependendo da vulnerabilidade, um SQL Injection pode permitir:

  • acessar informações que deveriam estar protegidas;
  • modificar dados;
  • excluir dados;
  • contornar mecanismos de autenticação;
  • descobrir estrutura do banco;
  • acessar registros de outros usuários;
  • em determinados cenários, comprometer outros componentes.

5. Como evitar SQL Injection?

A principal defesa é utilizar consultas parametrizadas (prepared statements).

Em vez de montar uma consulta juntando strings:

SQL + entrada do usuário

a aplicação separa:

SQL
+
parâmetros

Conceitualmente:

Consulta:
SELECT * FROM usuarios WHERE email = ?

Parâmetro:
gustavo@email.com

O banco entende que o valor é um dado, e não parte da estrutura SQL.

Exemplo com PHP e PDO

$sql = "SELECT * FROM usuarios WHERE email = :email";

$stmt = $pdo->prepare($sql);

$stmt->execute([
    ':email' => $email
]);

Essa é uma das técnicas fundamentais para prevenir SQL Injection.

6. NoSQL Injection

Aplicações modernas também utilizam bancos NoSQL, como:

  • MongoDB;
  • CouchDB;
  • Redis;
  • Cassandra;
  • entre outros.

Eles possuem mecanismos diferentes dos bancos SQL, mas também podem apresentar vulnerabilidades de injeção.

O problema pode ocorrer quando uma aplicação aceita estruturas fornecidas pelo usuário e as utiliza diretamente em consultas.

Por exemplo:

Dados do usuário
       ↓
Objeto/estrutura de consulta
       ↓
Banco NoSQL

Se a aplicação não controlar corretamente os tipos e valores recebidos, o atacante pode tentar alterar a lógica da consulta.

Proteções

É importante:

  • validar os tipos de dados;
  • utilizar APIs seguras do driver;
  • não aceitar estruturas arbitrárias quando não forem necessárias;
  • validar campos permitidos;
  • limitar operadores;
  • utilizar bibliotecas atualizadas.

7. Command Injection

Outra categoria importante é a Command Injection.

Nesse caso, o alvo não é necessariamente o banco de dados, mas o sistema operacional.

Imagine uma aplicação que permite executar alguma operação relacionada a arquivos.

Uma implementação insegura poderia fazer:

entrada do usuário
       ↓
comando do sistema
       ↓
Sistema operacional

Se a entrada for incorporada diretamente ao comando, existe o risco de o usuário conseguir modificar aquilo que será executado.

Consequências

Dependendo das permissões do processo, isso pode permitir:

  • executar comandos indevidos;
  • acessar arquivos;
  • modificar arquivos;
  • obter informações do sistema;
  • comprometer a aplicação;
  • eventualmente comprometer o servidor.

Esse tipo de vulnerabilidade é particularmente grave.

8. Como evitar Command Injection?

A melhor estratégia é não executar comandos do sistema a partir de entradas controladas pelo usuário quando isso puder ser evitado.

Quando for realmente necessário:

Valide a entrada

Defina exatamente o que pode ser recebido.

Por exemplo:

ID permitido:
12345

em vez de aceitar qualquer texto.

Use listas permitidas

Em vez de:

aceitar qualquer comando

utilize:

ação = visualizar
ação = gerar
ação = excluir

A aplicação escolhe internamente o comando correspondente.

Evite shell quando possível

Bibliotecas e APIs específicas geralmente são mais seguras do que montar comandos manualmente.

9. LDAP Injection

O LDAP Injection ocorre quando uma aplicação utiliza informações fornecidas pelo usuário para construir consultas LDAP sem tratamento adequado.

LDAP é utilizado principalmente para:

  • diretórios;
  • autenticação;
  • gerenciamento de usuários;
  • ambientes corporativos.

Uma entrada manipulada pode alterar a lógica da consulta LDAP.

Proteção

Utilizar:

  • APIs apropriadas;
  • escaping adequado;
  • validação de entrada;
  • consultas construídas de forma segura;
  • controle dos campos permitidos.

10. XPath Injection

O XPath Injection ocorre em aplicações que trabalham com XML e utilizam XPath para realizar consultas.

O princípio é semelhante ao SQL Injection:

Entrada do usuário
       ↓
Consulta XPath
       ↓
XML

Se a entrada for incorporada diretamente à consulta, ela poderá alterar sua lógica.

A prevenção envolve:

  • validação;
  • escaping;
  • evitar concatenação insegura;
  • utilização de mecanismos apropriados para consultas parametrizadas quando disponíveis.

11. Template Injection

Aplicações web frequentemente utilizam sistemas de templates para gerar páginas.

Exemplos de tecnologias que trabalham com templates incluem:

  • Twig;
  • Jinja;
  • Handlebars;
  • alguns sistemas de templates de JavaScript;
  • sistemas de templates de diversas linguagens.

Uma vulnerabilidade pode ocorrer quando uma aplicação permite que o usuário controle diretamente uma parte do template que será interpretado pelo servidor.

Isso pode resultar em Server-Side Template Injection (SSTI).

Fluxo

Entrada do usuário
       ↓
Template
       ↓
Interpretador
       ↓
Servidor

Dependendo da tecnologia e configuração, o impacto pode ser muito grave.

12. XSS também é uma forma de injeção

O Cross-Site Scripting (XSS) também está relacionado ao conceito de injeção.

Nesse caso, o atacante tenta fazer com que conteúdo fornecido por ele seja interpretado como código pelo navegador da vítima.

Por exemplo:

Usuário envia conteúdo
       ↓
Aplicação armazena/exibe
       ↓
Navegador interpreta
       ↓
Código pode ser executado

Existem três categorias clássicas:

  • Stored XSS;
  • Reflected XSS;
  • DOM-based XSS.

A prevenção normalmente envolve:

  • escaping de saída;
  • sanitização quando apropriada;
  • validação;
  • uso correto de APIs do navegador;
  • Content Security Policy (CSP);
  • evitar inserir conteúdo não confiável diretamente no HTML.

13. Injeção de cabeçalhos HTTP

Também existem ataques nos quais a entrada do usuário é inserida em cabeçalhos HTTP.

Se a aplicação não controlar corretamente caracteres e valores, um atacante pode tentar manipular a resposta ou o comportamento de componentes intermediários.

Isso pode estar relacionado a problemas como:

  • HTTP Header Injection;
  • CRLF Injection;
  • manipulação de redirecionamentos;
  • problemas de cache em determinados cenários.

A defesa envolve:

  • validação rigorosa;
  • utilização de APIs que tratam cabeçalhos corretamente;
  • impedir caracteres de controle;
  • não permitir que usuários controlem cabeçalhos arbitrários.

14. O problema central: confiança excessiva na entrada

Um conceito extremamente importante em segurança é:

Nunca considere automaticamente confiável uma entrada recebida do usuário.

Entradas podem vir de:

  • formulários;
  • URL;
  • parâmetros GET;
  • parâmetros POST;
  • cookies;
  • headers;
  • APIs;
  • arquivos;
  • JSON;
  • banco de dados;
  • integrações externas.

Mesmo que a interface gráfica limite o que o usuário pode inserir, um atacante pode ignorar completamente essa interface e enviar requisições diretamente.

Por isso:

Frontend
   ↓
Backend
   ↓
Validação
   ↓
Processamento seguro

A validação deve acontecer principalmente no servidor.

15. Validação × Sanitização × Parametrização

Esses conceitos são importantes e não são exatamente a mesma coisa.

Validação

Verifica se a entrada está dentro do que é permitido.

Exemplo:

Idade:
18 → válida
abc → inválida

Sanitização

Modifica ou remove determinados elementos potencialmente perigosos.

Parametrização

Mantém os dados separados da instrução.

É especialmente importante para SQL.

Podemos resumir:

Validação       → "Esse dado é permitido?"
Sanitização     → "Como tornar esse dado seguro?"
Parametrização  → "Como impedir que dado vire comando?"

16. Princípio do menor privilégio

Mesmo que uma vulnerabilidade de injeção aconteça, o impacto pode ser reduzido utilizando privilégio mínimo.

Por exemplo, uma aplicação que apenas precisa consultar dados não deveria utilizar uma conta do banco com permissão para:

SELECT
INSERT
UPDATE
DELETE
DROP
ALTER
...

Se ela só precisa:

SELECT

deveria receber apenas essa permissão.

Isso reduz o dano potencial caso a aplicação seja comprometida.

18. Boas práticas contra ataques de injeção

Uma aplicação segura deve combinar várias medidas:

1. Validar entradas

Defina:

  • tipo;
  • tamanho;
  • formato;
  • valores permitidos;
  • caracteres permitidos quando aplicável.

2. Utilizar parametrização

Principalmente para consultas ao banco.

❌ SQL + string do usuário

✅ SQL + parâmetros

3. Evitar concatenação de comandos

Não construa comandos de sistema utilizando entradas diretamente.

4. Utilizar APIs seguras

Prefira bibliotecas oficiais e mecanismos preparados para tratar dados.

5. Aplicar escaping corretamente

Especialmente quando dados são colocados em contextos como:

  • HTML;
  • JavaScript;
  • SQL;
  • XML;
  • URLs;
  • headers.

O escaping necessário depende do contexto.

6. Aplicar menor privilégio

Reduza as permissões da aplicação e de seus usuários técnicos.

7. Manter dependências atualizadas

Bibliotecas vulneráveis também podem abrir caminhos para exploração.

8. Monitorar logs

Registre eventos relevantes para identificar comportamentos anormais.

9. Utilizar WAF quando apropriado

Um Web Application Firewall pode ajudar a detectar e bloquear determinados padrões maliciosos.

Porém, ele não substitui a correção da aplicação.

10. Realizar testes de segurança

Incluindo:

  • análise de código;
  • testes automatizados;
  • testes de segurança;
  • análise de dependências;
  • pentests autorizados.

19. Exemplo de uma aplicação vulnerável e segura

Imagine um sistema que pesquisa usuários.

❌ Abordagem insegura

Entrada do usuário
       ↓
Concatenação
       ↓
Consulta SQL
       ↓
Banco

O problema é que a entrada pode modificar a consulta.

✅ Abordagem segura

Entrada
   ↓
Validação
   ↓
Consulta parametrizada
   ↓
Banco

A consulta e os dados permanecem separados.

21. Resumo

Injeção acontece quando dados fornecidos por uma fonte não confiável são interpretados como comandos, consultas ou código.

Os principais exemplos são:

TipoPrincipal alvo
SQL InjectionBanco SQL
NoSQL InjectionBanco NoSQL
Command InjectionSistema operacional
LDAP InjectionDiretórios LDAP
XPath InjectionXML/XPath
Template InjectionSistemas de templates
XSSNavegador
Header InjectionComunicação HTTP

A ideia fundamental para memorizar é:

              ENTRADA
                 │
                 ▼
        ┌─────────────────┐
        │ Aplicação segura│
        └────────┬────────┘
                 │
       ┌─────────┴─────────┐
       ▼                   ▼
     DADOS              COMANDOS
       │                   │
       └────── separados ──┘

A melhor defesa contra injeção é impedir que dados sejam interpretados como instruções. Para isso, utilizamos principalmente validação de entrada, parametrização, APIs seguras, escaping adequado, menor privilégio e testes de segurança.

Esse conceito é fundamental para quem desenvolve aplicações web, pois uma única entrada tratada de maneira incorreta pode afetar desde o navegador até o banco de dados ou o próprio servidor.
