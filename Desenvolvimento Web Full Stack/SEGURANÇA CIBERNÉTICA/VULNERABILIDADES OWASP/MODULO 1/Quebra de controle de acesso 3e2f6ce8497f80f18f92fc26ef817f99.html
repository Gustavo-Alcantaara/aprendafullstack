Quebra de Controle de Acesso

A Quebra de Controle de Acesso (Broken Access Control) é uma vulnerabilidade em que uma aplicação permite que um usuário acesse recursos, informações ou funcionalidades que ele não deveria poder acessar.

Em outras palavras, o sistema possui regras sobre quem pode fazer o quê, mas essas regras não são aplicadas corretamente.

É um problema muito importante em aplicações web porque pode permitir que um usuário comum consiga acessar dados ou funcionalidades pertencentes a outros usuários ou até mesmo a administradores.

1. O que é Controle de Acesso?

Antes de entender a quebra, precisamos entender o controle de acesso.

O controle de acesso determina quais ações cada usuário pode realizar dentro de um sistema.

Por exemplo, em uma aplicação podemos ter:

Usuário comum
 ├── Ver seu perfil
 ├── Alterar seu perfil
 └── Ver seus pedidos

Administrador
 ├── Ver usuários
 ├── Editar usuários
 ├── Excluir usuários
 └── Gerenciar sistema

A aplicação precisa verificar essas permissões antes de executar cada operação.

Podemos representar:

Usuário
   ↓
Autenticação
   ↓
"Quem é você?"
   ↓
Autorização
   ↓
"O que você pode fazer?"
   ↓
Recurso

2. Autenticação × Autorização

Essa diferença é fundamental.

Autenticação

Responde:

Quem é você?

Exemplo:

Email: gusta@email.com
Senha: ********

O sistema verifica a identidade do usuário.

Autorização

Responde:

O que você pode fazer?

Por exemplo:

Gusta
Cargo: usuário

Pode:
✓ visualizar próprio perfil
✓ editar próprio perfil

Não pode:
✗ excluir usuários
✗ acessar painel administrativo

Portanto:

Autenticação → identifica
Autorização  → determina permissões

Uma aplicação pode ter uma autenticação perfeitamente funcional e ainda possuir uma grave vulnerabilidade de controle de acesso.

3. O que é a quebra de controle de acesso?

A quebra ocorre quando o sistema não verifica corretamente as permissões antes de permitir determinada ação.

Imagine:

Usuário A
   ↓
/perfil/123

O usuário deveria conseguir visualizar somente o perfil 123, caso esse seja o seu próprio perfil.

Mas ele altera o identificador:

/perfil/124

e consegue visualizar os dados de outra pessoa.

Nesse caso:

Usuário A
   ↓
Solicita recurso de Usuário B
   ↓
Servidor não verifica propriedade
   ↓
Acesso concedido

Isso é um exemplo clássico de problema de controle de acesso.

4. Um dos principais exemplos: IDOR

Um caso muito conhecido é o IDOR — Insecure Direct Object Reference.

Ocorre quando uma aplicação utiliza um identificador direto para acessar um recurso, mas não verifica se o usuário possui autorização para acessá-lo.

Por exemplo:

https://site.com/pedido/1001

O usuário possui o pedido:

1001

Mas também consegue acessar:

1002
1003
1004

mesmo que esses pedidos pertençam a outras pessoas.

O problema não é necessariamente o número do pedido existir na URL.

O problema é:

O servidor não verificou se aquele usuário tem permissão para acessar aquele objeto.

5. Exemplo prático

Imagine uma API:

GET /api/pedidos/150

O backend recebe:

pedido_id = 150

Uma implementação vulnerável poderia simplesmente fazer:

buscar pedido 150
↓
retornar pedido

Mas deveria fazer algo parecido com:

buscar pedido 150
       ↓
verificar proprietário
       ↓
pedido pertence ao usuário?
       ↓
   ┌───┴───┐
  SIM     NÃO
   ↓       ↓
Permitir  Negar

Esse detalhe é fundamental.

6. Controle de acesso baseado em funções

Um modelo bastante utilizado é o RBAC — Role-Based Access Control.

Nesse modelo, usuários recebem funções (roles).

Por exemplo:

ADMIN
MODERADOR
USUARIO

Cada função possui determinadas permissões.

Exemplo

FunçãoVer perfilCriar conteúdoExcluir conteúdoGerenciar usuários
Usuário✓✓✗✗
Moderador✓✓✓✗
Administrador✓✓✓✓

O problema acontece quando a aplicação não verifica corretamente essas permissões.

7. Escalação horizontal de privilégios

A escalação horizontal acontece quando um usuário acessa recursos pertencentes a outro usuário com o mesmo nível de privilégio.

Exemplo:

Usuário A
   ↓
Tenta acessar
   ↓
Dados do Usuário B

Ambos são usuários comuns.

A → B

Não houve necessariamente mudança de função.

O usuário simplesmente conseguiu acessar recursos que pertenciam a outra conta.

Exemplo

Imagine:

/usuario/100

pertencente a:

Gusta

E:

/usuario/101

pertencente a:

João

Se Gusta conseguir acessar /usuario/101 sem autorização, existe uma falha de controle de acesso.

8. Escalação vertical de privilégios

Aqui a situação é diferente.

Um usuário com poucos privilégios consegue acessar funções de um usuário com mais privilégios.

Por exemplo:

Usuário comum
      ↓
Painel administrativo

Ou:

Usuário comum
      ↓
Excluir usuários

Ou:

Usuário comum
      ↓
Alterar configurações do sistema

Representação:

Usuário
   │
   └──────► Administrador
              ↑
        privilégio maior

Isso é chamado de escalação vertical de privilégios.

9. Controle de acesso no frontend não é suficiente

Esse é um erro muito comum.

Imagine que uma aplicação esconda um botão:

<button style="display:none">
    Excluir usuário
</button>

Isso não significa que a operação está protegida.

Um usuário pode tentar realizar a requisição diretamente.

A proteção precisa existir no backend.

❌ Segurança apenas no frontend

Frontend
   ↓
"Botão escondido"
   ↓
Parece protegido

✅ Segurança no backend

Requisição
   ↓
Backend
   ↓
Verificação de permissão
   ↓
Permitido?
 ┌──┴──┐
SIM   NÃO
 ↓     ↓
Executa 403

O frontend pode esconder funcionalidades por questões de interface, mas a autorização real deve ser aplicada no servidor.

10. Métodos HTTP e controle de acesso

As APIs geralmente utilizam métodos HTTP como:

GET     → consultar
POST    → criar
PUT     → substituir/atualizar
PATCH   → atualizar parcialmente
DELETE  → excluir

Cada operação precisa verificar autorização.

Por exemplo:

GET /usuarios/10

pode exigir determinada permissão.

Já:

DELETE /usuarios/10

pode exigir uma permissão administrativa.

Não basta verificar:

"usuário está logado?"

É necessário verificar:

"usuário está autorizado a realizar ESTA operação?"

11. Erros comuns que causam a vulnerabilidade

Confiar em dados enviados pelo usuário

Por exemplo:

{
    "role": "admin"
}

A aplicação nunca deveria confiar cegamente nesse valor para decidir as permissões do usuário.

As permissões devem ser determinadas pelo servidor.

Esconder funcionalidades no frontend

Como vimos:

botão escondido ≠ autorização

Verificar apenas se o usuário está autenticado

Isso:

if (usuarioLogado)

não significa necessariamente:

if (usuarioPodeExecutarEstaAcao)

Não verificar propriedade do recurso

Por exemplo:

pedido = buscarPedido(id)

sem verificar:

pedido.usuario_id == usuario.id

quando essa relação for necessária.

Permissões inconsistentes

Uma aplicação pode proteger:

POST /usuarios

mas esquecer de proteger:

DELETE /usuarios

ou alguma outra rota equivalente.

Por isso, a autorização precisa ser pensada para todas as operações relevantes.

12. Controle de acesso em uma aplicação web

Podemos visualizar uma aplicação moderna assim:

                 USUÁRIO
                    │
                    ▼
               FRONTEND
                    │
                    ▼
                  API
                    │
                    ▼
               BACKEND
                    │
             ┌──────┴──────┐
             ▼             ▼
          BANCO          SERVIÇOS

Em cada requisição importante, o backend precisa verificar:

1. Quem é o usuário?
2. Qual recurso ele está tentando acessar?
3. Qual operação ele está tentando executar?
4. Ele possui permissão?
5. O recurso pertence a ele?
6. Existem outras regras de negócio?

13. Exemplo com PHP

Imagine uma página de edição de usuários:

/editar_usuario.php?id=10

Uma implementação segura precisa descobrir quem está realizando a operação.

Conceitualmente:

if (!$usuarioLogado) {
    // negar acesso
}

if (!$usuarioPodeEditar) {
    // negar acesso
}

E, dependendo da regra:

if ($usuarioDoRecurso !== $usuarioLogado) {
    // negar acesso
}

A ideia principal não é simplesmente verificar se o usuário está logado, mas verificar se ele possui autorização para aquela ação específica.

14. Códigos HTTP importantes

As APIs utilizam códigos HTTP para comunicar o resultado das operações.

401 Unauthorized

Normalmente indica que a requisição não possui uma autenticação válida ou necessária.

Exemplo:

Usuário não autenticado

403 Forbidden

Indica que o servidor entendeu a requisição, mas o usuário não possui permissão suficiente.

Exemplo:

Usuário comum tentando acessar função administrativa.

Uma forma simples de memorizar:

401 → problema de autenticação
403 → acesso não permitido

15. Princípio do menor privilégio

Uma das principais defesas é o Princípio do Menor Privilégio.

Cada usuário deve possuir somente as permissões necessárias para realizar suas tarefas.

Por exemplo:

Usuário comum
↓
Somente recursos próprios

Moderador
↓
Recursos de moderação

Administrador
↓
Recursos administrativos

Evite conceder:

TODAS AS PERMISSÕES

para todos os usuários.

Quanto mais permissões uma conta possui, maior pode ser o impacto caso ela seja comprometida.

16. Deny by Default

Outro princípio importante é:

Negar por padrão e permitir explicitamente o que for necessário.

Em vez de:

Tudo permitido
↓
bloquear algumas coisas

preferimos:

Tudo bloqueado
↓
liberar somente o necessário

Por exemplo:

/usuario
   ↓
permitido para usuários autenticados

/admin
   ↓
permitido somente para administradores

/admin/usuarios/excluir
   ↓
permitido somente para quem possui essa permissão

17. Como prevenir Quebra de Controle de Acesso?

Uma aplicação deve utilizar várias camadas de proteção.

1. Verificar autorização no servidor

A decisão final deve ser feita pelo backend.

2. Não confiar no frontend

Elementos escondidos ou desabilitados não são mecanismos de segurança.

3. Implementar RBAC ou outro modelo adequado

Defina claramente:

usuário
↓
função
↓
permissões

4. Verificar propriedade dos recursos

Pergunte:

Esse recurso pertence ao usuário?

quando aplicável.

5. Aplicar menor privilégio

Conceda somente as permissões necessárias.

6. Negar por padrão

Recursos devem ser protegidos explicitamente.

7. Centralizar regras de autorização

Evite espalhar verificações diferentes e inconsistentes pela aplicação.

8. Testar todas as rotas

Principalmente:

GET
POST
PUT
PATCH
DELETE

9. Testar diferentes papéis

Por exemplo:

Usuário
Moderador
Administrador

10. Registrar eventos importantes

Logs podem ajudar a identificar tentativas de acesso indevido.

18. Controle de acesso e banco de dados

O banco também pode participar da segurança.

Imagine:

Usuário A
   ↓
Backend
   ↓
Banco

Uma consulta deve respeitar as regras de propriedade.

Por exemplo, conceitualmente:

SELECT *
FROM pedidos
WHERE id = ?
AND usuario_id = ?;

Assim, a aplicação não está simplesmente procurando:

WHERE id = ?

mas também relacionando o recurso ao usuário autorizado.

Isso ajuda a reduzir o risco de acesso indevido a objetos.

19. Defesa em profundidade

Uma aplicação segura não deve depender de uma única verificação.

Podemos ter:

                 Requisição
                     │
                     ▼
              Autenticação
                     │
                     ▼
              Autorização
                     │
                     ▼
           Verificação de recurso
                     │
                     ▼
            Regra de negócio
                     │
                     ▼
                 Banco

Isso é conhecido como defesa em profundidade.

Se uma camada apresentar um problema, outras camadas podem limitar o impacto.

20. Exemplo completo

Imagine um sistema de loja virtual.

Gusta está autenticado:

Usuário: Gusta
ID: 25

Ele possui:

Pedido 100
Pedido 101

Outro usuário possui:

Pedido 102

Gusta solicita:

GET /pedidos/102

O sistema vulnerável faz:

Pedido encontrado?
    ↓
SIM
    ↓
Retorna pedido

Isso é problemático.

O sistema seguro deveria fazer:

Pedido encontrado?
       ↓
      SIM
       ↓
Pertence ao usuário 25?
    ┌──┴──┐
   SIM   NÃO
    ↓     ↓
 Permite  403

Assim, o simples conhecimento do identificador do pedido não é suficiente para obter acesso.

21. Impactos de uma quebra de controle de acesso

Dependendo do sistema e da vulnerabilidade, podem ocorrer:

  • exposição de dados pessoais;
  • acesso a contas de outros usuários;
  • alteração de informações;
  • exclusão de dados;
  • acesso ao painel administrativo;
  • alteração de permissões;
  • acesso a informações confidenciais;
  • operações financeiras indevidas;
  • comprometimento de recursos administrativos.

A gravidade depende principalmente de qual recurso pode ser acessado e quais ações podem ser realizadas.

22. O que memorizar

Para sua matéria de Segurança Cibernética, os conceitos mais importantes são:

CONTROLE DE ACESSO
        │
        ├── Autenticação
        │      └── Quem é você?
        │
        └── Autorização
               └── O que você pode fazer?

Quebra de Controle de Acesso ocorre quando essas regras não são aplicadas corretamente.

Os conceitos fundamentais são:

  • Broken Access Control
  • IDOR
  • Escalação horizontal
  • Escalação vertical
  • RBAC
  • Menor privilégio
  • Deny by Default
  • Autorização no backend
  • Verificação de propriedade
  • 401 vs 403

Resumo final

Autenticação
     ↓
Quem é o usuário?
     ↓
Autorização
     ↓
O que ele pode fazer?
     ↓
Qual recurso ele pode acessar?
     ↓
Ação permitida ou negada

A ideia central é simples:

Estar autenticado não significa estar autorizado.

Uma aplicação segura deve verificar quem é o usuário, qual recurso ele está tentando acessar e se ele possui permissão para realizar aquela ação, sempre no lado do servidor.
