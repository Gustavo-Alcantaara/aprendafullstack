Falsificação de Requisição

Falsificação de Requisição do Lado do Servidor — SSRF

A Falsificação de Requisição do Lado do Servidor, conhecida como SSRF — Server-Side Request Forgery, é uma vulnerabilidade que ocorre quando uma aplicação permite que um usuário influencie qual recurso ou endereço o servidor acessará, sem validar adequadamente essa entrada.

Em termos simples:

O atacante faz o servidor realizar uma requisição que ele próprio não deveria realizar.

Esse conceito é particularmente importante em aplicações modernas porque servidores frequentemente precisam acessar outros serviços, APIs, bancos, sistemas internos, armazenamento em nuvem e outros recursos.

1. Entendendo a ideia

Imagine uma aplicação que possui uma funcionalidade:

Usuário
   ↓
Envia uma URL
   ↓
Servidor
   ↓
Acessa essa URL
   ↓
Retorna o resultado

Por exemplo, uma aplicação pode permitir:

"Informe a URL de uma imagem para importá-la."

O usuário fornece:

https://exemplo.com/imagem.jpg

O servidor faz:

Servidor
   ↓
GET https://exemplo.com/imagem.jpg

Até aqui, tudo pode parecer normal.

O problema aparece quando o servidor aceita qualquer destino sem verificar se aquele endereço deveria ser acessível.

2. Onde está a vulnerabilidade?

O problema pode ser representado assim:

                 APLICAÇÃO
                    │
                    ▼
              URL fornecida
               pelo usuário
                    │
                    ▼
             Servidor realiza
             uma requisição
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
     Destino permitido    Destino indevido
          ↓                   ↓
        Normal             SSRF

O ponto principal é:

o servidor possui privilégios e acesso de rede que o usuário externo normalmente não possui.

Assim, o atacante tenta utilizar o servidor como um intermediário.

3. Por que "do lado do servidor"?

Porque quem realiza a requisição é o servidor da aplicação, e não diretamente o navegador do usuário.

Sem SSRF:

Navegador
    ↓
Internet
    ↓
Site externo

Com SSRF:

Navegador
    ↓
Aplicação
    ↓
Servidor
    ↓
Outro serviço

O atacante controla uma entrada da aplicação e tenta fazer com que o servidor seja quem acessa o destino.

4. Exemplo conceitual

Imagine uma aplicação que recebe:

URL: https://site.com/imagem.png

O backend faz algo semelhante a:

const resposta = await fetch(url);

O problema não está necessariamente no fetch().

O problema está em:

URL fornecida pelo usuário
          ↓
Nenhuma validação adequada
          ↓
fetch(url)

Se o servidor puder acessar destinos que não deveriam estar disponíveis ao usuário, a aplicação pode apresentar SSRF.

5. O que torna SSRF perigoso?

Um servidor normalmente possui acesso a recursos que não estão diretamente disponíveis na Internet.

Por exemplo:

Internet
   │
   ▼
Servidor Web
   │
   ├── API interna
   ├── Banco de dados
   ├── Painel administrativo
   ├── Outros servidores
   └── Serviços internos

O usuário externo talvez só consiga acessar:

https://site.com

Mas o servidor pode conseguir conversar com vários outros serviços.

A SSRF tenta explorar essa diferença.

6. SSRF e serviços internos

Imagine uma arquitetura:

                INTERNET
                    │
                    ▼
              ┌──────────┐
              │ Front/API│
              └────┬─────┘
                   │
          ┌────────┼────────┐
          ↓        ↓        ↓
       Serviço   Serviço   Banco
       interno   interno

Os serviços internos podem não estar expostos diretamente à Internet.

Porém:

Internet
   ↓
Aplicação vulnerável
   ↓
Rede interna
   ↓
Serviço interno

A aplicação pode acabar funcionando como uma ponte entre o atacante e a rede interna.

7. SSRF não significa necessariamente acesso ao banco

É importante evitar uma simplificação comum.

SSRF não significa automaticamente:

"O atacante consegue acessar o banco."

O impacto depende da arquitetura.

Pode permitir acesso a:

  • APIs internas;
  • painéis administrativos;
  • serviços de monitoramento;
  • sistemas internos;
  • endpoints de gerenciamento;
  • serviços de infraestrutura;
  • recursos de ambientes cloud.

Em outros casos, pode simplesmente fazer o servidor acessar um site externo.

O impacto depende de para onde o servidor consegue se conectar e o que esses serviços permitem fazer.

8. SSRF em ambientes de nuvem

Esse é um dos cenários mais importantes.

Ambientes de cloud frequentemente possuem serviços internos de infraestrutura, incluindo mecanismos que fornecem informações ou credenciais temporárias para recursos autorizados.

Se uma aplicação vulnerável conseguir acessar esses serviços indevidamente, o impacto pode ser significativo.

O fluxo conceitual seria:

Atacante
   ↓
Aplicação vulnerável
   ↓
Serviço interno de infraestrutura
   ↓
Informações/credenciais temporárias
   ↓
Possível comprometimento adicional

Por isso, aplicações em cloud precisam de proteções específicas contra SSRF.

9. SSRF clássica x SSRF cega

Existem diferentes formas de SSRF.

SSRF clássica

O servidor realiza a requisição e o conteúdo pode retornar para o atacante.

Atacante
   ↓
Aplicação
   ↓
Servidor acessa destino
   ↓
Resposta
   ↓
Aplicação
   ↓
Atacante

O atacante consegue observar a resposta.

SSRF cega — Blind SSRF

Em uma Blind SSRF, o servidor realiza a requisição, mas o atacante não recebe diretamente o conteúdo da resposta.

Atacante
   ↓
Aplicação
   ↓
Servidor
   ↓
Destino interno

A resposta pode não ser retornada.

Mesmo assim, a requisição pode causar efeitos importantes.

Por exemplo, ela pode:

  • atingir um serviço interno;
  • gerar uma ação;
  • modificar algum estado;
  • produzir um evento;
  • revelar informações indiretamente.

10. SSRF em funcionalidades comuns

SSRF pode aparecer em funcionalidades que parecem completamente legítimas.

Importação de URL

"Digite a URL do arquivo"

Gerador de preview

URL
 ↓
Servidor busca página
 ↓
Gera preview

Webhooks

Sistema
 ↓
URL configurada
 ↓
Envia requisição

Integrações externas

Aplicação
 ↓
API externa

Conversores

URL
 ↓
Servidor baixa conteúdo
 ↓
Converte

Processamento de imagens

URL da imagem
 ↓
Servidor baixa imagem
 ↓
Processa

Qualquer funcionalidade em que o servidor busque um recurso baseado em uma entrada controlada pelo usuário merece atenção.

11. Exemplo em uma aplicação Full Stack

Imagine uma API Node.js:

app.post("/preview", async (req, res) => {
    const { url } = req.body;

    const response = await fetch(url);

    const data = await response.text();

    res.send(data);
});

Conceitualmente:

POST /preview
       ↓
{ "url": "..." }
       ↓
fetch(url)
       ↓
Servidor acessa URL

O problema é que url está sendo controlada pelo cliente.

A aplicação está dizendo:

"Você me informa para onde eu devo fazer uma requisição."

Isso exige validação muito cuidadosa.

12. O problema não é simplesmente "aceitar URL"

É importante entender isso.

Não significa que:

fetch(url)

seja sempre inseguro.

O problema aparece quando existe uma combinação como:

Entrada controlada pelo usuário
          +
Servidor realiza requisição
          +
Validação insuficiente
          +
Destino potencialmente perigoso

Portanto, SSRF é principalmente um problema de confiança e validação do destino.

13. Como prevenir SSRF?

A principal estratégia é não permitir que o usuário escolha livremente qualquer destino que o servidor possa acessar.

Existem várias camadas de proteção.

13.1 Allowlist

Uma das abordagens mais seguras é utilizar uma lista de destinos permitidos.

Por exemplo:

Destinos permitidos:

api.exemplo.com
cdn.exemplo.com
storage.exemplo.com

O servidor rejeita qualquer outro destino.

URL recebida
    ↓
Está na allowlist?
   ↙       ↘
 SIM       NÃO
 ↓          ↓
Permite    Bloqueia

Quando o conjunto de destinos conhecidos é pequeno, essa abordagem é especialmente interessante.

14. Validar o esquema da URL

A aplicação deve verificar o protocolo utilizado.

Por exemplo:

https://

pode ser permitido, enquanto outros esquemas podem ser desnecessários ou perigosos dependendo da biblioteca e do ambiente.

A aplicação deve aceitar apenas os esquemas necessários ao caso de uso.

15. Validar host e porta

Também é importante verificar:

Host
Porta
Esquema

Por exemplo, se a aplicação só precisa acessar uma API HTTPS específica, não existe motivo para permitir arbitrariamente:

qualquer host
qualquer porta
qualquer protocolo

Quanto menor o conjunto de destinos possíveis, menor a superfície de ataque.

16. Cuidado com redirecionamentos

Esse é um detalhe muito importante.

Imagine:

URL permitida
      ↓
Servidor acessa
      ↓
Redirecionamento
      ↓
Outro destino

A aplicação pode validar inicialmente:

https://site-permitido.com

mas o servidor seguir um redirecionamento para outro endereço.

Por isso, o tratamento de redirects também precisa fazer parte da validação.

17. Não confiar apenas no nome do domínio

Imagine que a aplicação verifique apenas:

host.endsWith("exemplo.com")

Uma validação ingênua pode ser enganada por nomes de domínio que apenas contenham aquele texto.

A validação precisa utilizar mecanismos apropriados de análise de URL e regras precisas.

18. Proteção contra destinos internos

Dependendo do caso de uso, a aplicação deve bloquear o acesso a destinos que não deveriam ser alcançáveis pelo usuário.

Isso inclui, por exemplo, determinados:

  • endereços de loopback;
  • endereços privados;
  • endereços de link-local;
  • interfaces internas;
  • redes administrativas.

A ideia é:

Internet
   ↓
Aplicação
   ↓
❌ Rede interna protegida

19. Mas bloquear IPs não é suficiente

Existe uma dificuldade importante.

A aplicação pode verificar um domínio:

api.exemplo.com

e descobrir um endereço aparentemente permitido.

Depois, o endereço pode mudar ou resolver de maneira diferente.

Por isso, a proteção precisa considerar o processo completo de resolução e conexão, e não apenas uma verificação superficial da URL.

Esse é um dos motivos pelos quais SSRF pode ser uma vulnerabilidade tecnicamente difícil de prevenir corretamente.

20. Controle de saída da rede

Uma defesa muito importante ocorre fora da aplicação.

Podemos limitar quais destinos o servidor consegue acessar:

Aplicação
    │
    ▼
Firewall / controle de saída
    │
    ├── API autorizada → ✅
    ├── Serviço interno → ❌
    └── Rede administrativa → ❌

Isso é chamado de controle de egress ou tráfego de saída.

Mesmo que a aplicação possua uma vulnerabilidade, a infraestrutura pode impedir determinados acessos.

21. Princípio do menor privilégio

O servidor não deveria ter acesso irrestrito à rede.

Se uma aplicação precisa acessar apenas:

api.pagamentos.com

não existe necessidade de permitir:

qualquer endereço
qualquer porta
qualquer rede

Isso segue o princípio:

Conceda apenas os acessos necessários.

22. Segmentação de rede

Uma arquitetura bem segmentada pode reduzir o impacto de uma SSRF.

Por exemplo:

                 Internet
                    │
                    ▼
              ┌──────────┐
              │ Web/API  │
              └────┬─────┘
                   │
          ┌────────┴────────┐
          ↓                 ↓
      Serviços           Banco
      permitidos        protegido

Se a camada web for comprometida, ela não deveria automaticamente conseguir acessar tudo dentro da infraestrutura.

23. Proteção em cloud

Em ambientes de cloud, é importante combinar:

Aplicação
   +
Validação de URL
   +
Controle de egress
   +
IAM com menor privilégio
   +
Proteção de serviços de metadata

Assim, mesmo que uma SSRF exista, o impacto potencial pode ser reduzido.

24. Não confiar no frontend

Imagine que o frontend tenha:

if (url.startsWith("https://site-permitido.com")) {
    enviar(url);
}

Isso não é suficiente.

Um usuário pode simplesmente ignorar o frontend e enviar uma requisição diretamente para a API.

A validação precisa existir no:

BACKEND

e, quando aplicável, também na infraestrutura.

25. SSRF e outras vulnerabilidades

SSRF pode funcionar como uma etapa de uma cadeia de ataque.

Por exemplo:

SSRF
 ↓
Acesso a serviço interno
 ↓
Falha de autenticação
 ↓
Acesso indevido
 ↓
Comprometimento

Ou:

SSRF
 ↓
Serviço interno
 ↓
Informação sensível
 ↓
Vazamento

Por isso, SSRF frequentemente deve ser analisada em conjunto com:

  • controle de acesso;
  • autenticação;
  • segmentação de rede;
  • configurações de cloud;
  • gerenciamento de credenciais.

26. Como identificar SSRF durante o desenvolvimento?

Pergunte:

A aplicação recebe uma URL do usuário?

Sim → atenção

O servidor realiza uma requisição baseada nessa URL?

Sim → atenção

O usuário pode escolher livremente o destino?

Sim → risco maior

Existem destinos permitidos?

Não → melhorar validação

O servidor possui acesso à rede interna?

Sim → impacto potencial maior

Existem controles de saída?

Não → adicionar segmentação/egress

27. Checklist de prevenção

[ ] O servidor realmente precisa buscar URLs fornecidas pelo usuário?
[ ] Existe uma allowlist de destinos quando possível?
[ ] O esquema da URL é validado?
[ ] Host e porta são validados?
[ ] Redirecionamentos são controlados?
[ ] Destinos internos são bloqueados quando apropriado?
[ ] A resolução DNS é tratada de forma segura?
[ ] O frontend não é a única camada de validação
[ ] Existe controle de tráfego de saída
[ ] A rede está segmentada
[ ] O servidor possui apenas os acessos necessários
[ ] Credenciais de infraestrutura possuem menor privilégio
[ ] Serviços internos não são expostos desnecessariamente
[ ] Logs registram requisições suspeitas
[ ] Existem alertas para comportamentos anormais

28. Exemplo de arquitetura mais segura

Uma aplicação que precisa baixar imagens poderia seguir:

                 USUÁRIO
                    │
                    ▼
              URL fornecida
                    │
                    ▼
             ┌─────────────┐
             │ Validação   │
             └──────┬──────┘
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
      Permitido            Bloqueado
          │                   │
          ▼                   ▼
    Cliente HTTP            Rejeitar
          │
          ▼
   Controle de saída
          │
          ▼
    Destino permitido

Dessa forma, a segurança não depende de uma única barreira.

29. SSRF x CSRF

Os nomes podem causar confusão porque ambos possuem "CSRF/SSRF" e envolvem requisições, mas são vulnerabilidades diferentes.

SSRF

Server-Side Request Forgery

Atacante
   ↓
Servidor
   ↓
Servidor faz requisição

O objetivo é abusar da capacidade do servidor de realizar requisições.

CSRF

Cross-Site Request Forgery

Vítima autenticada
       ↓
Navegador
       ↓
Aplicação

O objetivo é induzir o navegador de uma vítima autenticada a realizar uma ação que ela não pretendia realizar.

Resumo:

SSRFCSRF
Abusa do servidorAbusa do navegador da vítima
Servidor realiza a requisiçãoNavegador realiza a requisição
Foco em acesso do servidorFoco em ações autenticadas
Pode atingir serviços internosPode executar ações em aplicações onde a vítima está autenticada

SSRF se conecta bastante com o que você já estudou:

AutenticaçãoServiços internos podem possuir mecanismos de autenticação inadequados

Resumo

SSRF — Server-Side Request Forgery é uma vulnerabilidade em que um atacante consegue influenciar uma aplicação para que o servidor realize requisições para destinos que não deveriam estar acessíveis daquela maneira.

O fluxo básico é:

Atacante
   ↓
Entrada controlada
   ↓
Aplicação vulnerável
   ↓
Servidor realiza requisição
   ↓
Destino indevido

O risco aumenta quando o servidor possui acesso a:

Redes internas
Serviços administrativos
APIs internas
Infraestrutura cloud
Serviços de gerenciamento

As principais defesas são:

Allowlist
    +
Validação rigorosa de URLs
    +
Controle de redirects
    +
Bloqueio de destinos internos quando necessário
    +
Controle de egress
    +
Segmentação de rede
    +
Menor privilégio
    +
Proteções específicas de cloud
    +
Monitoramento

Ideia principal

Nunca presuma que uma URL fornecida pelo usuário é segura apenas porque ela parece legítima. Se o servidor vai realizar uma requisição em nome do usuário, o destino precisa ser tratado como entrada não confiável e validado adequadamente.
