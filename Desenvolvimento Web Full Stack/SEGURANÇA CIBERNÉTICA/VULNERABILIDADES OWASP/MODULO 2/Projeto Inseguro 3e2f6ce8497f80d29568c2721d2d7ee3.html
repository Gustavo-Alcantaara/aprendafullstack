Projeto Inseguro

No contexto de Segurança Cibernética, Projeto Inseguro (Security Misconfiguration / Insecure Design, dependendo do contexto) se refere a situações em que uma aplicação ou sistema é projetado ou configurado de maneira que introduz riscos de segurança.

É importante separar dois conceitos:

  • Projeto inseguro → o problema está nas decisões de arquitetura, requisitos ou lógica de segurança.
  • Configuração insegura → o sistema até poderia ser seguro, mas foi configurado incorretamente.

Em aplicações modernas, ambos podem resultar em vulnerabilidades graves.

1. O que significa um projeto inseguro?

Um sistema possui um projeto inseguro quando a segurança não foi considerada adequadamente durante sua concepção.

Por exemplo, imagine um sistema bancário que permita:

Usuário
   ↓
Solicitação de transferência
   ↓
Transferência realizada

Mas o projeto não prevê nenhuma confirmação adicional para operações de alto risco.

O problema não está necessariamente em uma linha de código específica.

O problema pode estar na própria regra de negócio:

"Qualquer usuário autenticado pode realizar qualquer transferência sem nenhuma verificação adicional."

Isso é uma decisão de projeto.

2. Segurança deve fazer parte do projeto

Um erro comum é pensar:

1. Construir aplicação
2. Terminar tudo
3. Adicionar segurança

Uma abordagem mais adequada é:

Requisitos
    ↓
Projeto
    ↓
Desenvolvimento
    ↓
Testes
    ↓
Deploy
    ↓
Monitoramento

A segurança deve estar presente durante todo o ciclo.

Esse conceito é frequentemente chamado de Security by Design.

3. Projeto inseguro × código vulnerável

Esses conceitos podem parecer iguais, mas existe uma diferença.

Código vulnerável

O projeto pode estar correto, mas a implementação contém um erro.

Exemplo:

Projeto:
"Somente administradores podem excluir usuários."

Código:
não verifica se o usuário é administrador.

Nesse caso, existe um problema de implementação.

Projeto inseguro

A própria regra foi projetada de maneira inadequada.

Exemplo:

Projeto:
"Qualquer usuário autenticado pode excluir qualquer usuário."

Mesmo que o código implemente perfeitamente essa regra, o sistema continua inseguro.

4. Exemplos de Projeto Inseguro

Existem vários exemplos.

4.1. Ausência de controle de acesso

Imagine:

Usuário autenticado
       ↓
Pode acessar qualquer recurso

Se o projeto não define corretamente quem pode acessar cada recurso, o sistema pode permitir acesso indevido.

Um projeto mais seguro define:

Usuário
 ↓
Recursos próprios

Moderador
 ↓
Recursos de moderação

Administrador
 ↓
Recursos administrativos

5. Confiar apenas no frontend

Imagine um sistema administrativo.

O projeto decide:

"Se o botão de administrador estiver escondido,
o usuário não poderá executar a operação."

Isso é uma abordagem insegura.

O frontend não deve ser considerado uma barreira de segurança.

O correto é:

Frontend
   ↓
Backend
   ↓
Autorização
   ↓
Operação

Mesmo que o botão não apareça, o servidor precisa verificar a permissão.

6. Falta de proteção para operações críticas

Algumas operações são naturalmente mais sensíveis.

Por exemplo:

Alterar senha
Alterar e-mail
Excluir conta
Transferir dinheiro
Alterar permissões
Excluir registros
Alterar configurações

Um projeto inseguro pode tratar essas ações como se fossem operações comuns.

Por exemplo:

Usuário autenticado
      ↓
Alterar e-mail
      ↓
Pronto

Um projeto mais cuidadoso pode exigir mecanismos adicionais, dependendo do risco:

Usuário autenticado
       ↓
Solicita alteração
       ↓
Verificação adicional
       ↓
Confirmação
       ↓
Alteração

7. Recuperação de senha mal projetada

O mecanismo de recuperação de senha é um excelente exemplo.

Imagine:

Esqueci minha senha
       ↓
Informo e-mail
       ↓
Sistema envia link
       ↓
Nova senha

O projeto precisa considerar:

  • expiração do token;
  • uso único;
  • aleatoriedade adequada;
  • proteção contra reutilização;
  • limitação de tentativas;
  • não exposição de informações desnecessárias;
  • invalidação apropriada após a alteração.

Se essas questões não forem consideradas no projeto, pode surgir uma vulnerabilidade mesmo que o código esteja funcionando conforme especificado.

8. Perguntas de segurança no projeto

Um projeto seguro deve fazer perguntas como:

Sobre usuários

Quem pode acessar?
Quem pode alterar?
Quem pode excluir?

Sobre dados

Quais dados são sensíveis?
Onde serão armazenados?
Quem pode acessá-los?

Sobre autenticação

Como o usuário será autenticado?
Como a sessão será protegida?
Como a recuperação de senha funcionará?

Sobre autorização

Quais permissões existem?
Quem recebe cada permissão?

Sobre ataques

O que acontece se um usuário enviar dados maliciosos?
O que acontece se uma conta for comprometida?

9. Threat Modeling

Uma técnica muito importante para evitar projetos inseguros é o Threat Modeling, ou modelagem de ameaças.

A ideia é analisar o sistema antes ou durante seu desenvolvimento para identificar possíveis ameaças.

Podemos pensar:

Sistema
   ↓
Ativos
   ↓
Ameaças
   ↓
Riscos
   ↓
Controles

Exemplo

Imagine uma loja virtual.

Ativos

Contas
Pedidos
Dados pessoais
Pagamentos
Banco de dados

Ameaças

Roubo de conta
Acesso indevido
Manipulação de pedidos
Exposição de dados

Controles

MFA
Controle de acesso
HTTPS
Validação
Logs
Monitoramento

Esse processo permite identificar problemas antes que eles cheguem à produção.

10. Princípio do menor privilégio

O projeto também deve considerar o menor privilégio.

Cada usuário ou componente deve possuir somente as permissões necessárias.

Por exemplo:

Aplicação Web
      ↓
Banco de dados

Se a aplicação apenas precisa consultar determinados dados, não é uma boa decisão dar a ela acesso administrativo completo ao banco.

Em vez disso:

Aplicação
   ↓
Permissões necessárias

e não:

Aplicação
   ↓
TODAS as permissões

11. Fail Secure

Outro conceito importante é Fail Secure.

Significa que, quando algo dá errado, o sistema deve preferencialmente assumir uma postura segura.

Imagine que o sistema não consiga determinar se um usuário possui permissão.

Uma abordagem insegura seria:

Não consegui verificar
       ↓
Permitir acesso

Uma abordagem mais segura seria:

Não consegui verificar
       ↓
Negar acesso

Isso está relacionado ao princípio:

Na dúvida, não conceder privilégios automaticamente.

12. Não confiar em valores enviados pelo cliente

Imagine que o frontend envie:

{
  "usuario": "Gusta",
  "role": "admin"
}

Um projeto inseguro poderia confiar nesse valor.

Mas o cliente pode controlar a requisição.

Portanto:

Cliente
   ↓
Dados enviados
   ↓
Backend

O servidor precisa determinar as permissões utilizando informações confiáveis do lado do servidor.

13. Excesso de confiança no usuário

Outro problema de projeto é assumir que o usuário sempre seguirá o fluxo normal.

Por exemplo:

Passo 1 → escolher produto
Passo 2 → adicionar ao carrinho
Passo 3 → pagar
Passo 4 → finalizar

Um projeto inseguro pode assumir:

"O usuário sempre executará os passos nessa ordem."

Mas uma aplicação deve considerar que alguém pode tentar acessar diretamente uma etapa posterior.

O backend deve validar as condições necessárias.

14. Regras de negócio também precisam de segurança

Segurança não envolve somente:

senha
firewall
HTTPS
antivírus

As regras de negócio também podem apresentar vulnerabilidades.

Imagine um sistema que permita:

Saldo: R$ 100

Transferência:
R$ 150

Se o sistema não verifica corretamente o saldo, existe uma falha na lógica da aplicação.

Outro exemplo:

Cupom:
20% de desconto

O projeto pode precisar definir:

Pode utilizar uma vez?
Pode combinar com outro cupom?
Existe valor máximo?
Existe data de validade?

Se essas regras não forem projetadas corretamente, usuários podem explorar comportamentos inesperados.

15. Configuração insegura

Agora entramos em um conceito relacionado: Security Misconfiguration.

Aqui o sistema pode ter sido projetado de maneira adequada, mas sua configuração cria uma vulnerabilidade.

Exemplos:

❌ Senha padrão
❌ Serviços desnecessários ativados
❌ Painel administrativo exposto
❌ Mensagens de erro excessivamente detalhadas
❌ Permissões excessivas
❌ Configuração insegura do servidor
❌ Recursos de debug ativados em produção

Por exemplo:

Desenvolvimento:
DEBUG = ON

Produção:
DEBUG = ON  ← problema

Mensagens detalhadas podem revelar:

  • caminhos internos;
  • nomes de arquivos;
  • consultas;
  • versões;
  • informações da infraestrutura.

16. Mensagens de erro

Um sistema inseguro pode apresentar:

Erro:
MySQL connection failed at
C:\xampp\htdocs\projeto\config\database.php

Essa mensagem revela informações internas.

Uma aplicação de produção deveria apresentar algo mais controlado:

Não foi possível processar a solicitação.
Tente novamente mais tarde.

Enquanto os detalhes técnicos permanecem nos logs apropriados.

17. Configurações padrão

Outro problema comum são configurações padrão que nunca foram alteradas.

Exemplos:

Usuário padrão
Senha padrão
Chaves padrão
Portas desnecessárias
Serviços desnecessários

Uma aplicação deve revisar as configurações antes de entrar em produção.

18. Arquitetura segura

Um projeto moderno pode ser estruturado pensando em segurança desde o início:

                    INTERNET
                        │
                        ▼
                    HTTPS/TLS
                        │
                        ▼
                  ┌───────────┐
                  │    WAF    │
                  └─────┬─────┘
                        │
                        ▼
                  ┌───────────┐
                  │    API    │
                  └─────┬─────┘
                        │
              ┌─────────┴─────────┐
              ▼                   ▼
        Autenticação         Autorização
              │                   │
              └─────────┬─────────┘
                        ▼
                  Regras de negócio
                        │
                        ▼
                    Banco de dados

A segurança está distribuída por várias camadas.

19. Security by Design

O conceito de Security by Design significa incorporar segurança desde o início do desenvolvimento.

Em vez de:

Desenvolver
    ↓
Publicar
    ↓
Descobrir vulnerabilidades
    ↓
Corrigir

busca-se:

Requisitos
    ↓
Análise de ameaças
    ↓
Projeto seguro
    ↓
Implementação
    ↓
Testes de segurança
    ↓
Deploy
    ↓
Monitoramento

Isso reduz a probabilidade de problemas estruturais chegarem à produção.

20. Princípios importantes

Alguns princípios ajudam a evitar projetos inseguros.

Menor privilégio

Dar somente as permissões necessárias.

Deny by Default

Negar acesso por padrão e liberar explicitamente o necessário.

Fail Secure

Quando uma verificação falhar, não conceder privilégios automaticamente.

Defense in Depth

Utilizar várias camadas de proteção.

Autenticação
     +
Autorização
     +
Validação
     +
Criptografia
     +
Monitoramento

Separação de responsabilidades

Evitar que um único componente tenha controle excessivo sobre todo o sistema.

21. Como identificar um projeto inseguro?

Durante a análise de uma aplicação, podemos perguntar:

Autenticação

  • Como os usuários são autenticados?
  • Como a recuperação de senha funciona?
  • Existe proteção contra tentativas excessivas?

Autorização

  • Quem pode acessar cada recurso?
  • O backend verifica as permissões?
  • Existe isolamento entre usuários?

Dados

  • Quais informações são sensíveis?
  • Como são armazenadas?
  • Como são transmitidas?

Regras de negócio

  • Existem limites?
  • Existem validações?
  • O usuário pode manipular o fluxo?

Erros

  • O sistema revela informações internas?
  • O modo debug está desativado em produção?

Infraestrutura

  • Existem serviços desnecessários?
  • Existem credenciais padrão?
  • Os componentes estão atualizados?

23. Exemplo completo

Imagine uma aplicação de gerenciamento de funcionários.

Projeto inseguro

Usuário faz login
      ↓
Recebe acesso ao sistema
      ↓
Pode informar qualquer ID
      ↓
Backend retorna o funcionário

Problemas:

❌ Não verifica propriedade
❌ Não verifica função
❌ Confia no ID enviado
❌ Não diferencia operações administrativas

Projeto mais seguro

Usuário
   ↓
Autenticação
   ↓
Identificação da função
   ↓
Verificação de autorização
   ↓
Verificação do recurso
   ↓
Regra de negócio
   ↓
Operação

Agora:

Usuário comum
→ seus próprios recursos

Gerente
→ recursos permitidos pela função

Administrador
→ operações administrativas autorizadas

24. Resumo

Projeto Inseguro ocorre quando decisões de arquitetura, regras de negócio, requisitos ou configurações não consideram adequadamente a segurança.

Os principais conceitos para memorizar são:

Projeto Inseguro
      │
      ├── Falta de Security by Design
      ├── Regras de negócio inseguras
      ├── Controle de acesso inadequado
      ├── Confiança excessiva no cliente
      ├── Privilégios excessivos
      ├── Falta de validações
      ├── Recuperação de senha insegura
      ├── Configurações inseguras
      └── Falta de análise de ameaças

A ideia central é:

Segurança não deve ser adicionada somente depois que a aplicação está pronta; ela deve fazer parte do projeto desde o início.

Um projeto seguro considera quem pode acessar o quê, quais dados precisam de proteção, quais ameaças existem, como as regras de negócio podem ser abusadas e como o sistema deve se comportar quando algo dá errado.
