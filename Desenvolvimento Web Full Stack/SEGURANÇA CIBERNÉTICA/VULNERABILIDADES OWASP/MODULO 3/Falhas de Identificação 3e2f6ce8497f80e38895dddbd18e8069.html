Falhas de Identificação e Autenticação

Falhas de Identificação e Autenticação são problemas de segurança que acontecem quando uma aplicação não consegue identificar ou verificar corretamente quem está tentando acessar um recurso.

Esse tema está diretamente relacionado a login, senhas, sessões, tokens, recuperação de contas e autenticação multifator (MFA).

Em termos simples:

Identificação responde "quem é você?" e autenticação responde "prove que você é essa pessoa".

1. Identificação x Autenticação

Embora os termos sejam frequentemente usados juntos, eles não são exatamente a mesma coisa.

Identificação

É quando o usuário informa sua identidade.

Por exemplo:

E-mail: usuario@email.com

A aplicação recebe:

"Quem está tentando entrar?"
        ↓
usuario@email.com

Autenticação

É a verificação dessa identidade.

Por exemplo:

E-mail: usuario@email.com
Senha: ********

A aplicação verifica:

Essas credenciais pertencem realmente a esse usuário?

Então:

Identificação → "Sou o usuário X"
Autenticação → "Prove que você é o usuário X"

2. Onde entram as Falhas de Autenticação?

Uma falha acontece quando o mecanismo responsável por verificar a identidade pode ser burlado, manipulado ou utilizado de maneira insegura.

Exemplo conceitual:

Usuário
   ↓
Login
   ↓
Autenticação
   ↓
❌ Implementação insegura
   ↓
Acesso indevido

O problema pode estar em:

  • senhas;
  • sessões;
  • tokens;
  • cookies;
  • recuperação de senha;
  • autenticação multifator;
  • criação de contas;
  • gerenciamento de credenciais;
  • mecanismos de login.

3. Exemplos de falhas

Existem diversas maneiras pelas quais uma autenticação pode ser implementada de forma insegura.

3.1 Senhas fracas

Permitir senhas muito simples aumenta o risco de comprometimento das contas.

Exemplos ruins:

123456
password
admin
qwerty
12345678

Uma aplicação também não deveria permitir senhas extremamente curtas ou fáceis de adivinhar.

4. Armazenamento inadequado de senhas

Esse é um dos pontos mais importantes.

Uma aplicação não deve armazenar senhas em texto puro.

❌ Incorreto

Banco de dados

usuario: Gusta
senha: minhaSenha123

Se o banco de dados for comprometido, as senhas podem ser diretamente expostas.

✅ Abordagem adequada

A senha deve ser armazenada utilizando uma função de hash apropriada para senhas, como:

  • Argon2;
  • bcrypt;
  • scrypt;
  • PBKDF2.

Por exemplo:

Senha digitada
      ↓
Função de derivação/hash
      ↓
Hash armazenado

Quando o usuário faz login:

Senha digitada
      ↓
Verificação
      ↓
Hash armazenado
      ↓
Correspondência?
   ↙       ↘
 SIM       NÃO
 ↓          ↓
Login      Negado

5. Hash não é criptografia

Essa diferença é fundamental.

Criptografia

É utilizada quando precisamos proteger uma informação e posteriormente recuperá-la utilizando uma chave.

Texto
  ↓
Criptografia
  ↓
Dados criptografados
  ↓
Descriptografia
  ↓
Texto

Hash de senha

É utilizado para armazenar uma representação derivada da senha que permita verificar a senha posteriormente sem precisar guardar a senha original.

Senha
  ↓
KDF / hash apropriado
  ↓
Valor armazenado

Para senhas, a aplicação normalmente deve utilizar algoritmos próprios para armazenamento de credenciais, e não simplesmente aplicar SHA-256 ou outro hash rápido.

6. Falta de proteção contra tentativas repetidas

Imagine uma tela de login:

E-mail: usuario@email.com
Senha: ________

Se a aplicação permitir tentativas ilimitadas:

Tentativa 1
Tentativa 2
Tentativa 3
...
Tentativa 100.000
...

isso aumenta o risco de ataques automatizados de tentativa de credenciais.

Por isso, sistemas podem utilizar mecanismos como:

  • rate limiting;
  • atrasos progressivos;
  • bloqueios temporários;
  • detecção de comportamento anormal;
  • CAPTCHA em determinados contextos;
  • MFA.

7. Credential Stuffing

Um problema importante é o credential stuffing.

Ele acontece quando credenciais obtidas de um vazamento de outro serviço são utilizadas para tentar entrar em outras contas.

Exemplo:

Site A
↓
Credenciais vazadas

E-mail: usuario@email.com
Senha: senha123

O atacante pode tentar essas mesmas credenciais em:

Site B
Site C
Site D

Isso funciona especialmente quando uma pessoa reutiliza a mesma senha em vários serviços.

Proteção

  • senhas únicas;
  • MFA;
  • detecção de tentativas automatizadas;
  • rate limiting;
  • monitoramento de autenticação.

8. Autenticação Multifator — MFA

A autenticação multifator adiciona uma camada adicional de proteção.

Sem MFA:

Senha
 ↓
Acesso

Com MFA:

Senha
 ↓
Segundo fator
 ↓
Acesso

Os fatores podem envolver:

Algo que você sabe

Senha
PIN

Algo que você possui

Celular
Token físico
Chave de segurança

Algo que você é

Biometria

O princípio é:

Comprometer apenas a senha não deveria ser suficiente para obter acesso.

9. Sessões

Depois que o usuário faz login, a aplicação precisa lembrar que ele está autenticado.

É aí que entram as sessões.

Um fluxo simplificado:

Usuário
   ↓
Login
   ↓
Servidor verifica credenciais
   ↓
Usuário autenticado
   ↓
Servidor cria sessão
   ↓
Cookie / token
   ↓
Próximas requisições

10. Problemas com sessões

Uma implementação inadequada de sessões pode causar problemas.

Por exemplo:

  • identificadores de sessão previsíveis;
  • sessões que nunca expiram;
  • sessões não invalidadas após logout;
  • cookies sem proteção adequada;
  • reutilização indevida de sessão;
  • ausência de renovação do identificador após autenticação.

11. Session Fixation

Um conceito importante é Session Fixation.

O problema ocorre quando um atacante consegue fazer com que a vítima utilize um identificador de sessão conhecido pelo atacante e, posteriormente, a vítima se autentica nessa mesma sessão.

De forma conceitual:

Atacante
   ↓
Sessão conhecida
   ↓
Vítima utiliza essa sessão
   ↓
Vítima realiza login
   ↓
Sessão passa a representar usuário autenticado

Uma proteção importante é regenerar o identificador da sessão após a autenticação.

12. Cookies de sessão

Quando cookies são utilizados para autenticação, algumas configurações são importantes.

Secure

Faz com que o cookie seja enviado apenas através de conexões HTTPS.

Secure

HttpOnly

Impede que scripts do lado do cliente acessem diretamente o cookie.

HttpOnly

Isso ajuda a reduzir determinados riscos relacionados a roubo de cookies via JavaScript.

SameSite

Ajuda a controlar o envio do cookie em contextos de requisições entre sites.

SameSite=Lax

ou outras configurações adequadas ao caso de uso.

13. Expiração de sessão

Imagine que um usuário entre em um sistema em um computador público.

Se a sessão permanecer válida indefinidamente:

Login
 ↓
Usuário vai embora
 ↓
Sessão continua válida
 ↓
Outra pessoa utiliza o navegador
 ↓
Conta continua acessível

Por isso, aplicações podem utilizar:

  • expiração por inatividade;
  • expiração absoluta;
  • logout;
  • invalidação de sessão;
  • revogação de tokens.

14. Logout inadequado

Um erro comum é pensar que logout significa apenas:

redirecionar para /login

Isso não necessariamente encerra a autenticação.

Um logout adequado deve invalidar o mecanismo de autenticação utilizado.

Por exemplo:

Logout
 ↓
Sessão/token invalidado
 ↓
Cookie removido quando aplicável
 ↓
Acesso autenticado encerrado

15. Recuperação de senha

O mecanismo de recuperação de senha também faz parte da autenticação.

Imagine:

"Esqueci minha senha"
          ↓
Digite seu e-mail
          ↓
Receba um link
          ↓
Crie nova senha

Esse processo precisa ser protegido.

O token de recuperação deve:

  • ser difícil de adivinhar;
  • possuir validade limitada;
  • ser associado à operação correta;
  • ser invalidado após utilização;
  • não expor informações desnecessárias.

16. Erros de recuperação de senha

Um sistema inseguro poderia revelar:

"E-mail encontrado!"

quando a conta existe, e:

"E-mail não cadastrado!"

quando não existe.

Isso permite que alguém descubra quais e-mails possuem contas.

Uma abordagem comum é utilizar uma resposta mais genérica:

"Se existir uma conta associada a esse endereço,
as instruções serão enviadas."

Assim, reduz-se a possibilidade de enumeração de usuários.

17. Enumeração de usuários

A enumeração acontece quando um sistema permite descobrir quais usuários existem.

Por exemplo:

Login

usuario1@email.com
→ senha incorreta

usuario2@email.com
→ usuário não encontrado

Essa diferença de resposta pode revelar informações.

Outro exemplo:

Recuperação de senha

email-existente@email.com
→ conta encontrada

email-inexistente@email.com
→ conta não encontrada

Isso pode ajudar um atacante a construir uma lista de contas válidas.

18. Tokens de autenticação

Aplicações modernas frequentemente utilizam tokens.

Um fluxo simplificado:

Login
  ↓
Servidor verifica credenciais
  ↓
Token emitido
  ↓
Cliente armazena/utiliza token
  ↓
Requisições posteriores
  ↓
Servidor valida token

Um token precisa ser protegido porque ele pode representar uma sessão autenticada.

Se alguém obtiver um token válido, dependendo da arquitetura, poderá utilizá-lo enquanto ele permanecer válido.

19. JWT

Um exemplo conhecido é o JWT — JSON Web Token.

Estruturalmente, um JWT possui:

Header.Payload.Signature

Por exemplo:

xxxxx.yyyyy.zzzzz

O token pode conter informações sobre o usuário e outras claims.

Mas é importante entender:

JWT não é automaticamente sinônimo de segurança.

É possível implementar uma autenticação baseada em JWT de maneira insegura.

Por exemplo:

  • aceitar tokens expirados;
  • não validar corretamente a assinatura;
  • utilizar chaves inadequadas;
  • colocar informações sensíveis desnecessárias no payload;
  • não possuir mecanismo de revogação quando necessário.

20. HTTPS é essencial

Credenciais e mecanismos de autenticação devem ser protegidos durante o transporte.

Sem HTTPS:

Usuário
   ↓
Rede
   ↓
Servidor

Os dados podem ficar expostos a determinados tipos de interceptação.

Com HTTPS:

Usuário
   ↓
HTTPS/TLS
   ↓
Servidor

O TLS protege a comunicação contra diversos tipos de interceptação e alteração durante o transporte.

21. Autenticação x Autorização

Esse é um conceito que você já viu em Quebra de Controle de Acesso, e é importante não confundir.

Autenticação

Pergunta:

Quem é você?
Login + senha

Autorização

Pergunta:

O que você pode fazer?
Usuário comum
    ↓
Pode visualizar pedidos

Administrador
    ↓
Pode visualizar e administrar usuários

Portanto:

AUTENTICAÇÃO
      ↓
Quem é você?
      ↓
AUTORIZAÇÃO
      ↓
O que você pode acessar?

Uma aplicação pode ter uma autenticação perfeitamente funcional e ainda possuir falhas de autorização.

22. Exemplo completo

Imagine um sistema de banco.

Etapa 1 — Identificação

CPF: 000.000.000-00

O sistema identifica a conta.

Etapa 2 — Autenticação

Senha

O sistema verifica a identidade.

Etapa 3 — MFA

Código adicional

Outro fator é verificado.

Etapa 4 — Sessão

Sessão autenticada

Etapa 5 — Autorização

Usuário autenticado
        ↓
Pode acessar
        ↓
Somente suas próprias informações

Cada etapa possui responsabilidades diferentes.

23. Principais causas

As falhas de identificação e autenticação podem surgir devido a:

  • senhas fracas;
  • armazenamento inadequado de senhas;
  • ausência de MFA quando necessário;
  • sessões mal implementadas;
  • tokens mal protegidos;
  • recuperação de senha insegura;
  • ausência de limitação de tentativas;
  • mensagens de erro excessivamente informativas;
  • sessões que não expiram;
  • cookies inseguros;
  • falta de HTTPS;
  • gerenciamento inadequado de credenciais;
  • autenticação implementada incorretamente.

26. Checklist de segurança

Para uma aplicação web:

[ ] Senhas não são armazenadas em texto puro
[ ] É utilizado hash/KDF apropriado para senhas
[ ] Existe proteção contra tentativas automatizadas
[ ] MFA é utilizado quando apropriado
[ ] Sessões possuem expiração
[ ] Sessões são invalidadas no logout
[ ] IDs de sessão são imprevisíveis
[ ] Sessão é regenerada após autenticação
[ ] Cookies possuem configurações de segurança adequadas
[ ] HTTPS é utilizado
[ ] Tokens possuem validade adequada
[ ] Tokens são validados corretamente
[ ] Recuperação de senha é protegida
[ ] Tokens de recuperação expiram
[ ] Tokens de recuperação são de uso único
[ ] Mensagens não facilitam enumeração de usuários
[ ] Credenciais não aparecem nos logs
[ ] Contas administrativas possuem proteção adicional

Resumo

Falhas de Identificação e Autenticação ocorrem quando uma aplicação não consegue proteger adequadamente o processo de identificar usuários e verificar suas identidades.

Os principais pontos são:

Identificação
    ↓
"Quem é você?"

Autenticação
    ↓
"Prove que você é essa pessoa."

Sessão
    ↓
"Continue autenticado."

Autorização
    ↓
"O que você pode fazer?"

Os problemas mais importantes incluem:

  • senhas fracas;
  • armazenamento inadequado de senhas;
  • ausência de MFA;
  • ataques automatizados;
  • sessões inseguras;
  • tokens mal protegidos;
  • recuperação de senha vulnerável;
  • enumeração de usuários;
  • cookies mal configurados;
  • falta de HTTPS.

A ideia central é:

Não basta ter uma tela de login. A aplicação precisa proteger todo o ciclo de vida da identidade: criação da conta, autenticação, sessão, recuperação de acesso, logout e gerenciamento das credenciais.
