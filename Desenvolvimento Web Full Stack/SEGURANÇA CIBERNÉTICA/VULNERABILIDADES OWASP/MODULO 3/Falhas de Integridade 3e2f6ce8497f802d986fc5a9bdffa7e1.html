Falhas de Integridade

Falhas de Integridade de Dados e Software

Falhas de Integridade de Dados e Software acontecem quando uma aplicação não consegue garantir que seus dados, arquivos, código ou componentes permaneçam corretos, confiáveis e não sejam alterados de maneira indevida.

Esse conceito é muito importante em segurança da informação porque não basta proteger os dados contra leitura. Também precisamos garantir que eles não sejam modificados, corrompidos ou substituídos de forma não autorizada.

Uma forma simples de entender:

Confidencialidade → "Quem pode ver?"
Integridade        → "Quem pode alterar?"
Disponibilidade    → "Quem pode acessar e quando?"

A integridade faz parte da conhecida tríade CIA da segurança da informação:

             SEGURANÇA
                 │
       ┌─────────┼─────────┐
       ↓         ↓         ↓
Confidencial. Integridade Disponib.

1. O que é integridade?

Integridade significa garantir que uma informação permaneça:

  • correta;
  • completa;
  • consistente;
  • confiável;
  • protegida contra alterações não autorizadas.

Imagine um sistema bancário:

Saldo original:
R$ 5.000,00

Se alguém conseguir alterar esse valor sem autorização:

R$ 5.000,00
      ↓
R$ 50.000,00

houve uma violação de integridade.

O problema não é necessariamente alguém ter visualizado o saldo.

O problema foi alguém conseguir alterá-lo indevidamente.

2. Integridade de dados

A integridade de dados está relacionada à garantia de que os dados armazenados e processados pela aplicação não sejam modificados de forma indevida.

Exemplos de dados:

Usuários
Pedidos
Produtos
Preços
Saldos
Mensagens
Documentos
Configurações
Logs

Uma aplicação deve conseguir determinar que:

Dado original
     ↓
Permanece correto
     ↓
Sem alterações não autorizadas

3. Integridade de software

A integridade não se aplica somente aos dados.

Também precisamos garantir a integridade do software.

Por exemplo:

Aplicação original
      ↓
Código legítimo
      ↓
Implantação
      ↓
Execução

Imagine que alguém substitua um arquivo da aplicação:

app.js original
      ↓
substituído
      ↓
app.js malicioso

A aplicação pode continuar funcionando, mas agora o código executado não é mais o código confiável originalmente desenvolvido.

Isso é uma violação de integridade do software.

4. Como uma falha pode acontecer?

Podemos representar de maneira geral:

Dado / Software legítimo
          ↓
       Alteração
          ↓
┌─────────┴─────────┐
↓                   ↓
Autorizada        Não autorizada
↓                   ↓
Normal              Falha

Uma alteração não autorizada pode ocorrer por:

  • vulnerabilidade;
  • acesso indevido;
  • credenciais comprometidas;
  • configuração incorreta;
  • malware;
  • dependência comprometida;
  • processo de implantação inseguro;
  • falta de validação;
  • erro humano.

5. Integridade x Confidencialidade

É importante não confundir.

Confidencialidade

Protege contra acesso não autorizado.

Atacante
   ↓
❌ Não deveria conseguir ler

Integridade

Protege contra alteração não autorizada.

Atacante
   ↓
❌ Não deveria conseguir modificar

Um sistema pode ter uma e não ter a outra.

Por exemplo:

Dados:
R$ 1.000,00

Atacante não consegue visualizar
        ↓
Confidencialidade protegida

Mas consegue modificar:
R$ 1.000 → R$ 10.000

        ↓
Integridade comprometida

6. Integridade x Autenticidade

Também existe uma relação próxima entre integridade e autenticidade.

Integridade

Pergunta:

O conteúdo foi alterado?

Autenticidade

Pergunta:

O conteúdo realmente veio de quem deveria ter enviado?

Por exemplo, ao receber um arquivo:

Arquivo
   ↓
Está intacto?
   ↓
Integridade

E:

Arquivo
   ↓
Veio realmente do fornecedor?
   ↓
Autenticidade

As duas propriedades frequentemente trabalham juntas.

7. Falhas de integridade em bancos de dados

Bancos de dados são um dos principais lugares onde a integridade precisa ser protegida.

Imagine uma tabela:

CLIENTES

id | nome  | saldo
---|-------|-------
1  | João  | 5000
2  | Maria | 3000

Se uma aplicação permitir alterações indevidas:

id | nome  | saldo
---|-------|-------
1  | João  | 500000

temos um problema de integridade.

8. Integridade referencial

No contexto de bancos de dados, existe um conceito específico chamado integridade referencial.

Imagine:

CLIENTE
id
1
2
3

e:

PEDIDO
id | cliente_id
10 | 1
11 | 2
12 | 3

O cliente_id referencia um cliente existente.

Se aparecer:

12 | 999

mas o cliente 999 não existir, teremos uma inconsistência.

Por isso, bancos relacionais utilizam mecanismos como:

PRIMARY KEY
FOREIGN KEY
UNIQUE
NOT NULL
CHECK

para ajudar a preservar a integridade dos dados.

9. Integridade através de restrições

Por exemplo:

CREATE TABLE usuarios (
    id INT PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL
);

Aqui temos algumas garantias:

PRIMARY KEY
↓
identificação única

UNIQUE
↓
não permite e-mails duplicados

NOT NULL
↓
campo obrigatório

Essas regras ajudam o banco a rejeitar determinados estados inválidos.

10. Integridade de transações

Outro conceito importante é a transação.

Imagine uma transferência:

Conta A:
R$ 1.000

Conta B:
R$ 500

Transferência de R$ 200:

A → -200
B → +200

O sistema não deve terminar em uma situação como:

A → -200
B → +0

ou:

A → -0
B → +200

A operação precisa manter a consistência.

Por isso, bancos de dados utilizam transações e propriedades ACID:

A → Atomicidade
C → Consistência
I → Isolamento
D → Durabilidade

A Atomicidade é particularmente importante:

A operação deve acontecer completamente ou não acontecer.

11. Alteração de dados sem autorização

Uma aplicação também pode apresentar falhas quando permite que usuários alterem dados que não deveriam modificar.

Imagine:

Usuário A
   ↓
Seu perfil

Ele deveria poder alterar:

nome
foto
telefone

Mas não:

id
saldo
tipo_de_conta
permissão

Se conseguir modificar esses campos indevidamente, existe uma falha de segurança.

Isso também se relaciona diretamente com o tema que você estudou anteriormente:

Quebra de Controle de Acesso.

12. Integridade de arquivos

Arquivos também precisam ser protegidos.

Imagine:

config.json

O sistema espera:

{
  "modo": "producao"
}

Mas alguém consegue modificar para:

{
  "modo": "desenvolvimento"
}

Dependendo da aplicação, isso pode provocar comportamentos inesperados ou insegurança.

Arquivos importantes incluem:

  • configurações;
  • código-fonte;
  • executáveis;
  • bibliotecas;
  • certificados;
  • arquivos de configuração;
  • scripts;
  • backups.

13. Hash para verificar integridade

Uma das técnicas utilizadas para verificar integridade é o hash.

Imagine um arquivo:

arquivo.zip

Aplicamos uma função de hash:

arquivo.zip
     ↓
SHA-256
     ↓
A1B2C3...

Se o arquivo for alterado:

arquivo.zip
     ↓
alteração
     ↓
SHA-256
     ↓
D9E8F7...

O resultado será diferente.

Assim podemos verificar:

Hash esperado
      ↓
   comparar
      ↓
Hash calculado

Se forem iguais, isso fornece evidência de que o conteúdo corresponde ao conteúdo esperado.

14. Importante: hash não impede alterações

Esse detalhe é fundamental.

Um hash pode ajudar a detectar alterações, mas não necessariamente impede que elas aconteçam.

Por exemplo:

Arquivo
   ↓
Hash
   ↓
Alguém altera arquivo
   ↓
Hash muda

O hash permite perceber a diferença.

Porém, se um atacante conseguir alterar tanto o arquivo quanto o hash armazenado, uma simples comparação pode não ser suficiente.

Por isso existem mecanismos mais fortes.

15. Assinaturas digitais

Uma assinatura digital pode fornecer garantias relacionadas à:

  • integridade;
  • autenticidade;
  • origem.

De maneira simplificada:

Dados
  ↓
Hash
  ↓
Assinatura com chave privada
  ↓
Assinatura digital

Quem recebe pode verificar utilizando a chave pública correspondente.

Dados + assinatura
        ↓
Verificação
        ↓
Válida?
   ↙       ↘
 SIM       NÃO
 ↓           ↓
Confiável   Rejeitar

Isso é muito utilizado para software, certificados, pacotes e documentos digitais.

16. Integridade de software e atualizações

Imagine que você baixe uma atualização:

Aplicação
    ↓
Nova versão
    ↓
Instalação

Como saber se o arquivo realmente veio do fornecedor e não foi modificado?

É possível utilizar mecanismos como:

Assinatura digital
        ↓
Verificação
        ↓
Instalação

Se a assinatura não for válida:

❌ Não instalar

Isso ajuda a proteger contra alterações indevidas durante a distribuição.

17. Supply Chain e integridade

Esse assunto também está diretamente relacionado à cadeia de suprimentos de software (Software Supply Chain).

Uma aplicação moderna pode depender de:

Aplicação
    ↓
Framework
    ↓
Biblioteca
    ↓
Dependência
    ↓
Pacote
    ↓
Fornecedor

Se algum elemento for comprometido:

Fornecedor
    ↓
Pacote comprometido
    ↓
Aplicação
    ↓
Usuários

Isso pode causar uma violação de integridade.

18. Exemplo de dependência comprometida

Imagine que seu projeto tenha:

meu-projeto
   ↓
biblioteca-A
   ↓
biblioteca-B

Se a biblioteca B for substituída por uma versão maliciosa:

biblioteca-B legítima
       ↓
substituída
       ↓
biblioteca-B comprometida

Sua aplicação pode acabar executando código que você nunca escreveu.

Esse é um dos motivos pelos quais é importante utilizar:

  • fontes confiáveis;
  • gerenciadores de dependências;
  • versões conhecidas;
  • assinaturas/verificações quando disponíveis;
  • análise de dependências;
  • controle de alterações.

19. Controle de versão

Ferramentas como Git também ajudam na integridade do software.

Imagine:

Commit 1
   ↓
Commit 2
   ↓
Commit 3

Cada alteração fica registrada.

Isso permite:

  • saber quem alterou;
  • saber quando alterou;
  • visualizar o que mudou;
  • comparar versões;
  • recuperar versões anteriores.

Por exemplo:

Código funcionando
      ↓
Alteração
      ↓
Problema
      ↓
Identificar commit
      ↓
Reverter alteração

O Git não substitui mecanismos de segurança, mas fornece uma camada importante de rastreabilidade e controle.

20. CI/CD e integridade

Em ambientes profissionais, pipelines de CI/CD podem ajudar a garantir que somente software validado seja implantado.

Um fluxo:

Desenvolvedor
      ↓
Git
      ↓
Pull Request
      ↓
Testes
      ↓
Análise de segurança
      ↓

      ↓

Isso reduz a possibilidade de alterações não revisadas chegarem à produção.

21. Controle de acesso e integridade

Não adianta possuir um banco de dados seguro se qualquer usuário puder alterá-lo.

Por isso:

Autenticação
     ↓
Quem é?
     ↓
Autorização
     ↓
O que pode fazer?
     ↓
Integridade
     ↓
O que pode alterar?

Exemplo:

Usuário comum
    ↓
Pode alterar seu nome

Administrador
    ↓
Pode alterar dados administrativos

O princípio do menor privilégio é fundamental.

Cada usuário, processo ou serviço deve possuir somente as permissões necessárias.

22. Logs e integridade

Os logs também precisam ter integridade.

Imagine:

Login realizado
Usuário X
14:30

Se alguém puder apagar ou alterar os logs:

14:30 → Login realizado

poderia desaparecer.

Isso prejudica:

  • investigação;
  • auditoria;
  • detecção de ataques;
  • análise de incidentes.

Por isso, sistemas importantes podem utilizar mecanismos para proteger logs contra alterações.

23. Backups e integridade

Backup não significa simplesmente:

"Tenho uma cópia."

É necessário garantir que a cópia seja válida e recuperável.

Imagine:

Banco original
      ↓
Backup corrompido

Quando ocorre um incidente:

Sistema comprometido
      ↓
Restaurar backup
      ↓
Backup também está corrompido
      ↓
❌ Recuperação falha

Por isso, backups devem ser:

  • testados;
  • protegidos;
  • versionados quando apropriado;
  • monitorados;
  • armazenados de forma adequada.

25. Como proteger a integridade?

Uma estratégia completa pode envolver:

Controle de acesso

Permitir alterações somente para usuários autorizados.

Menor privilégio

Dar somente as permissões necessárias.

Hashes

Detectar alterações em arquivos e dados quando apropriado.

Assinaturas digitais

Verificar autenticidade e integridade de software e outros artefatos.

HTTPS/TLS

Proteger a comunicação durante o transporte.

Transações

Garantir consistência das operações no banco de dados.

Constraints

Utilizar:

PRIMARY KEY
FOREIGN KEY
UNIQUE
NOT NULL
CHECK

Controle de versão

Registrar alterações no código.

Code review

Revisar mudanças antes da implantação.

CI/CD seguro

Automatizar testes e verificações.

Backups

Manter cópias protegidas e testadas.

Monitoramento

Detectar alterações inesperadas.

Resumo

Falhas de Integridade de Dados e Software acontecem quando uma aplicação não consegue garantir que seus dados, arquivos, código e componentes permaneçam corretos, consistentes e protegidos contra alterações não autorizadas.

Os principais conceitos são:

                 INTEGRIDADE
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
     Dados         Software        Arquivos
       │              │              │
       ↓              ↓              ↓
   Banco de       Código          Configurações
    dados        Dependências       Logs
       │              │              │
       └──────────────┼──────────────┘
                      ↓
             Alterações confiáveis

As principais proteções incluem:

  • controle de acesso;
  • menor privilégio;
  • constraints de banco;
  • transações;
  • hashes;
  • assinaturas digitais;
  • HTTPS/TLS;
  • Git;
  • code review;
  • CI/CD seguro;
  • proteção de dependências;
  • backups;
  • monitoramento.

Ideia principal

Integridade significa garantir que aquilo que deveria permanecer correto e confiável não seja alterado de maneira indevida.

Em uma aplicação Full Stack, isso precisa ser protegido desde o navegador e a API até o banco de dados, arquivos, dependências, código-fonte e processo de implantação.
