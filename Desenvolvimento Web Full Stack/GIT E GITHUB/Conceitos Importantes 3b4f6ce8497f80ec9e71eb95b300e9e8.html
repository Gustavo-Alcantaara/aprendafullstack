Controle de Versão com Git e Conceitos Importantes

Introdução

O Git é um Sistema de Controle de Versão Distribuído (DVCS – Distributed Version Control System) criado por Linus Torvalds em 2005 para gerenciar o desenvolvimento do kernel Linux. Atualmente, é o sistema de controle de versão mais utilizado no mundo.

O Git permite acompanhar todas as alterações realizadas em arquivos, possibilitando recuperar versões antigas, trabalhar em equipe, criar diferentes linhas de desenvolvimento e manter um histórico completo das modificações.

Em projetos de software, especialmente aqueles desenvolvidos por várias pessoas, o Git tornou-se praticamente indispensável.

O que é Controle de Versão?

Controle de versão é um sistema responsável por registrar todas as alterações realizadas em arquivos ao longo do tempo.

Imagine que você está criando um sistema em PHP.

Sem controle de versão, você poderia salvar vários arquivos assim:

projeto_final.php
projeto_final2.php
projeto_final_agora_vai.php
projeto_final_corrigido.php
projeto_final_definitivo.php

Isso rapidamente vira uma bagunça.

Com Git, existe apenas um projeto, mas todas as versões ficam armazenadas no histórico.

Por exemplo:

Versão 1
↓
Versão 2
↓
Versão 3
↓
Versão 4
↓
Versão Atual

Caso algo dê errado, basta voltar para qualquer versão anterior.

Problemas que o Git resolve

Antes do Git, equipes enfrentavam diversos problemas:

  • Sobrescrita de arquivos
  • Perda de código
  • Dificuldade em saber quem alterou algo
  • Conflitos entre programadores
  • Impossibilidade de desfazer alterações facilmente

Com Git, tudo isso é controlado.

O sistema registra:

  • Quem fez a alteração
  • Quando foi feita
  • Quais arquivos mudaram
  • O que foi modificado
  • Mensagem explicando a alteração

O que é um Sistema Distribuído?

O Git é distribuído.

Isso significa que cada desenvolvedor possui uma cópia completa do projeto.

Exemplo:

Servidor

        Projeto

      /     |      \
 João  Maria  Pedro

Cada um possui:

  • histórico completo
  • commits
  • branches
  • tags

Mesmo sem internet, é possível:

  • criar commits
  • criar branches
  • visualizar histórico
  • comparar versões

A internet só é necessária quando se deseja compartilhar alterações.

Git x GitHub

Essa é uma das maiores confusões para iniciantes.

Git

É o programa instalado no computador.

Responsável por:

  • controlar versões
  • criar commits
  • criar branches
  • comparar arquivos
  • unir alterações

Funciona totalmente offline.

GitHub

O GitHub é uma plataforma online para hospedar repositórios Git.

Ele permite:

  • armazenar projetos na nuvem
  • compartilhar código
  • trabalhar em equipe
  • revisar código
  • abrir Issues
  • criar Pull Requests
  • automatizar tarefas

Resumindo:

Git = Controle de Versão

GitHub = Hospedagem de projetos Git

Como o Git funciona?

O Git trabalha através de snapshots.

Muitos imaginam que ele salva apenas as diferenças.

Na realidade, cada commit representa uma fotografia do projeto naquele momento.

Exemplo:

Commit A

index.html
style.css

↓

Commit B

index.html
style.css
script.js

↓

Commit C

index.html
style.css
script.js
README.md

Cada commit representa um estado completo do projeto.

O que é um Repositório?

Repositório é a pasta monitorada pelo Git.

Toda alteração realizada nela poderá ser registrada.

Exemplo:

MeuProjeto/

index.html
style.css
script.js
.git

A pasta oculta:

.git

guarda todo o histórico do projeto.

Ela contém:

  • commits
  • branches
  • configurações
  • histórico
  • referências

Nunca se deve apagar essa pasta se quiser manter o histórico.

Conceitos Importantes do Git

Repositório (Repository)

É o local onde o projeto fica armazenado.

Pode ser:

  • Local
  • Remoto

Exemplo:

Computador → Repositório Local

GitHub → Repositório Remoto

Commit

O commit é o conceito mais importante do Git.

Um commit representa um ponto salvo da evolução do projeto.

Imagine um videogame.

Quando você salva o progresso, pode voltar exatamente para aquele ponto.

O commit funciona da mesma forma.

Exemplo:

Commit 1
"Projeto criado"

↓

Commit 2
"Tela de Login"

↓

Commit 3
"Banco conectado"

↓

Commit 4
"Correção de Bug"

Cada commit possui:

  • identificador único (hash)
  • autor
  • data
  • hora
  • mensagem

Hash

Cada commit possui um identificador exclusivo.

Exemplo:

a8d93ef7f12b8aa44f...

Esse código identifica exatamente aquele commit.

Nunca existirão dois commits iguais.

Histórico

Todo commit entra no histórico.

Exemplo:

Login criado

↓

Cadastro criado

↓

Banco conectado

↓

Tela corrigida

↓

Sistema publicado

É possível navegar entre todos eles.

Branch

Branch significa "ramo".

É uma linha paralela de desenvolvimento.

Exemplo:

main

|
|
|

feature-login

|
|

feature-pagamento

Isso permite desenvolver novas funcionalidades sem afetar a versão principal.

Quando estiver pronta, a branch pode ser unida à principal.

Merge

Merge significa unir duas branches.

Exemplo:

main

|
|

feature-login

↓

Merge

↓

main atualizada

As alterações passam para a branch principal.

Checkout

Permite mudar de branch ou voltar para um commit específico.

Exemplo:

main

↓

checkout

↓

feature-login

HEAD

HEAD representa a posição atual do Git.

Exemplo:

Commit A

↓

Commit B

↓

Commit C ← HEAD

HEAD aponta para o commit em que você está trabalhando.

Working Directory

É a pasta onde você edita os arquivos.

Exemplo:

index.html
style.css
app.js

Qualquer alteração acontece primeiro aqui.

Staging Area (Área de Preparação)

Antes de criar um commit, o Git permite escolher quais alterações farão parte dele.

Essa área intermediária é chamada de Staging Area ou Index.

Fluxo:

Arquivo editado

↓

Staging Area

↓

Commit

Isso permite criar commits organizados, contendo apenas mudanças relacionadas.

Untracked Files

Arquivos que ainda não são monitorados pelo Git.

Exemplo:

novoArquivo.php

Enquanto não forem adicionados ao Git, permanecem como untracked.

Tracked Files

São arquivos já conhecidos pelo Git.

Toda alteração futura será monitorada automaticamente.

Modified Files

Arquivos que foram alterados após o último commit.

Exemplo:

index.html

(modificado)

Staged Files

Arquivos já preparados para o próximo commit.

Remote

É uma referência para um repositório remoto.

Normalmente:

origin

representa o repositório hospedado no GitHub.

Clone

Clonar significa copiar um repositório remoto para o computador.

Resultado:

GitHub

↓

Clone

↓

Computador

Todo o histórico também é copiado.

Push

Envia commits locais para o repositório remoto.

Local

↓

Push

↓

GitHub

Pull

Baixa alterações do repositório remoto.

GitHub

↓

Pull

↓

Computador

Fetch

Baixa as alterações do servidor sem aplicá-las automaticamente ao seu trabalho local.

Permite revisar o que mudou antes de integrar essas alterações.

Conflito (Conflict)

Ocorre quando duas alterações incompatíveis afetam a mesma parte de um arquivo.

Exemplo:

João altera:

echo "Olá";

Maria altera:

echo "Bem-vindo";

Ao tentar unir as mudanças, o Git não consegue decidir qual manter e solicita que o desenvolvedor resolva o conflito manualmente.

Fluxo Básico de Trabalho no Git

O ciclo mais comum é:

Criar ou editar arquivos
        │
        ▼
Working Directory
        │
        ▼
git add
        │
        ▼
Staging Area
        │
        ▼
git commit
        │
        ▼
Repositório Local
        │
        ▼
git push
        │
        ▼
Repositório Remoto (GitHub)

Vantagens do Git

  • Controle completo do histórico do projeto.
  • Facilidade para desfazer alterações.
  • Desenvolvimento paralelo com branches.
  • Trabalho colaborativo entre equipes.
  • Identificação de autoria das mudanças.
  • Integração com plataformas como GitHub, GitLab e Bitbucket.
  • Funcionamento offline para a maior parte das operações.
  • Segurança por meio do armazenamento distribuído.

Boas Práticas

  • Faça commits pequenos e frequentes, cada um representando uma única alteração lógica.
  • Escreva mensagens de commit claras e descritivas, como "Adiciona validação de login" em vez de "Atualização".
  • Use branches para desenvolver novas funcionalidades ou corrigir bugs, evitando trabalhar diretamente na branch principal.
  • Mantenha o repositório sincronizado com o remoto usando fetch e pull regularmente.
  • Nunca altere ou exclua a pasta .git manualmente.

Erros Comuns

  • Fazer um único commit com muitas alterações diferentes.
  • Trabalhar diretamente na branch main em projetos colaborativos.
  • Esquecer de adicionar arquivos à Staging Area antes do commit.
  • Escrever mensagens de commit vagas, como "teste" ou "mudanças".
  • Ignorar conflitos de merge sem analisá-los cuidadosamente.

Resumo

O Git é um sistema de controle de versão distribuído que registra a evolução de um projeto por meio de commits, permitindo recuperar versões anteriores, trabalhar em equipe e desenvolver funcionalidades em paralelo com branches. Conceitos como repositório, Staging Area, HEAD, merge, push e pull formam a base do seu funcionamento. Dominar esses conceitos é essencial para qualquer desenvolvedor, pois eles sustentam fluxos de trabalho profissionais e colaborativos em praticamente todos os projetos de software modernos.
