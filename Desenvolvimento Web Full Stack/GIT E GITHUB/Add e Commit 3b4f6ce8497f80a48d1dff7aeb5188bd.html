Add e Commit no Git

Introdução

Os comandos git add e git commit são dois dos comandos mais importantes do Git e fazem parte do fluxo básico de controle de versão. Juntos, eles permitem registrar alterações no histórico do projeto de forma organizada.

Embora sejam frequentemente usados em sequência, eles têm funções diferentes:

  • git add: seleciona quais alterações serão incluídas no próximo commit.
  • git commit: salva essas alterações no histórico do repositório.

Entender a diferença entre esses comandos é essencial para criar um histórico de versões claro e organizado.

O Fluxo de Trabalho do Git

Antes de estudar os comandos, é importante entender o fluxo de trabalho do Git.

Working Directory
(Arquivos sendo editados)
          │
          ▼
      git add
          │
          ▼
    Staging Area
 (Área de Preparação)
          │
          ▼
     git commit
          │
          ▼
 Repositório Local

O Git trabalha em três áreas principais:

  1. Working Directory – Onde os arquivos são criados e editados.
  1. Staging Area (Index) – Área temporária onde são selecionadas as alterações que farão parte do próximo commit.
  1. Repositório Local – Onde os commits ficam armazenados permanentemente.

O que é o git add?

O comando git add adiciona arquivos à Staging Area, preparando-os para serem registrados no próximo commit.

Ele não salva as alterações definitivamente. Apenas informa ao Git quais mudanças devem fazer parte do próximo registro.

Imagine um carrinho de compras:

  • Você escolhe os produtos → git add
  • Você finaliza a compra → git commit

Como Funciona o git add

Suponha que você tenha os seguintes arquivos:

MeuProjeto/
│
├── index.html
├── style.css
└── script.js

Você modifica:

  • index.html
  • style.css

Executando:

git status

Resultado:

Changes not staged for commit:

modified: index.html
modified: style.css

Os arquivos foram alterados, mas ainda não estão preparados para o commit.

Agora execute:

git add index.html

Novo status:

Changes to be committed:

modified: index.html

Changes not staged for commit:

modified: style.css

Apenas index.html foi preparado.

Principais Formas de Usar o git add

Adicionar um único arquivo

git add index.html

Adicionar vários arquivos

git add index.html style.css

Adicionar todos os arquivos

git add .

O ponto (.) representa todos os arquivos da pasta atual e de suas subpastas.

Adicionar todos os arquivos modificados e removidos

git add -u

Esse comando adiciona apenas arquivos que já eram monitorados pelo Git.

Adicionar tudo, incluindo arquivos novos

git add -A

Inclui:

  • Arquivos novos.
  • Arquivos modificados.
  • Arquivos removidos.

O que é a Staging Area?

A Staging Area é uma área intermediária entre a edição dos arquivos e o commit.

Ela permite selecionar exatamente quais alterações serão registradas.

Exemplo:

Working Directory

index.html
style.css
script.js

        │

git add index.html

        ▼

Staging Area

index.html

        │

git commit

        ▼

Commit criado

Isso permite criar commits organizados, mesmo quando vários arquivos foram modificados.

Verificando a Área de Preparação

Após executar git add, utilize:

git status

Exemplo:

Changes to be committed:

modified: index.html

modified: style.css

Esses arquivos já estão preparados para o próximo commit.

Removendo Arquivos da Staging Area

Caso tenha adicionado um arquivo por engano:

git restore --staged index.html

O arquivo sai da Staging Area, mas continua com suas alterações no diretório de trabalho.

O que é o git commit?

O comando git commit registra permanentemente no histórico todas as alterações que estão na Staging Area.

Cada commit representa um snapshot (fotografia) do projeto em um determinado momento.

Depois de criado, o commit passa a fazer parte da linha do tempo do projeto.

Como Funciona o git commit

Após adicionar arquivos:

git add .

Criamos o commit:

git commit -m "Adiciona tela de login"

O Git registra:

  • Os arquivos modificados.
  • A data e a hora.
  • O autor.
  • A mensagem do commit.
  • Um identificador único (hash).

Estrutura de um Commit

Cada commit possui informações importantes.

Exemplo:

Commit: a7d91ef

Autor: João Silva

Data: 06/08/2026

Mensagem:

"Adiciona tela de login"

O hash identifica o commit de forma única.

A Opção m

A opção -m permite informar a mensagem diretamente na linha de comando.

git commit -m "Corrige erro no cadastro"

Sem -m:

git commit

O Git abrirá o editor configurado para que a mensagem seja escrita.

A Importância da Mensagem de Commit

A mensagem deve explicar claramente o que foi alterado.

Bons exemplos

Adiciona tela de login

Corrige validação do formulário

Atualiza documentação

Remove código duplicado

Implementa autenticação JWT

Maus exemplos

teste

alteração

mudanças

aaa

corrigido

Mensagens vagas dificultam a compreensão do histórico.

Visualizando os Commits

Após criar um commit:

git log

Ou:

git log --oneline

Exemplo:

5a2f8b3 Corrige menu

9ab31f1 Adiciona login

4de1200 Projeto inicial

Exemplo Prático

Imagine o seguinte projeto:

MeuProjeto/

index.html

style.css

Você modifica os dois arquivos.

Verifica o status:

git status

Resultado:

modified: index.html

modified: style.css

Adiciona apenas um arquivo:

git add index.html

Agora:

Staging Area

index.html

Cria o commit:

git commit -m "Atualiza página inicial"

Apenas index.html será registrado.

style.css continuará modificado, aguardando outro commit.

Quando Fazer um Commit?

O ideal é criar um commit sempre que uma alteração lógica estiver concluída.

Exemplos:

  • Finalizou uma tela.
  • Corrigiu um bug.
  • Implementou uma funcionalidade.
  • Atualizou a documentação.
  • Refatorou um módulo.

Evite esperar dias para criar um único commit com dezenas de alterações.

Commits Pequenos x Commits Grandes

Commit pequeno (recomendado)

Commit 1

Cria tela de login

Commit 2

Valida formulário

Commit 3

Conecta ao banco

Commit 4

Corrige layout

Vantagens:

  • Fácil de entender.
  • Fácil de revisar.
  • Fácil de desfazer.

Commit grande (não recomendado)

"Atualizações diversas"

Dentro dele:

  • Login.
  • Cadastro.
  • Banco.
  • CSS.
  • API.
  • Documentação.

Esse tipo de commit dificulta a manutenção do projeto.

Boas Práticas

  • Faça commits pequenos e frequentes.
  • Utilize mensagens objetivas e descritivas.
  • Adicione apenas arquivos relacionados ao mesmo contexto.
  • Revise as alterações com git status e git diff antes de criar um commit.
  • Use a Staging Area para organizar quais alterações farão parte de cada commit.
  • Agrupe mudanças relacionadas em um único commit e evite misturar funcionalidades diferentes.

Erros Comuns

  • Esquecer de executar git add antes do git commit.
  • Utilizar git add . sem verificar quais arquivos estão sendo adicionados.
  • Criar commits com mensagens genéricas, como "teste" ou "corrigido".
  • Fazer um único commit contendo várias funcionalidades diferentes.
  • Acreditar que git add já salva as alterações definitivamente; na verdade, ele apenas prepara os arquivos para o commit.

Resumo

Os comandos git add e git commit são a base do controle de versão no Git. O git add envia arquivos para a Staging Area, permitindo selecionar exatamente quais alterações serão registradas. Em seguida, o git commit cria um novo ponto no histórico do projeto, armazenando permanentemente essas alterações com uma mensagem descritiva. Utilizados corretamente, esses comandos ajudam a manter um histórico organizado, facilitam a colaboração em equipe e tornam a manutenção do projeto muito mais eficiente.
